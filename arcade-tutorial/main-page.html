    A Tour of the Arcade

    Before writing any code, it helps to know what the finished project looks like from the outside. The Math Arcade is a static website: a folder of HTML, CSS and JavaScript files that a server hands to the browser exactly as they are. There is no build step and no server code of our own. Everything the arcade "does" happens in the player's browser.

    The folder

    Here is the part of the math-arcade/ folder that these two courses cover:

    Notice the pattern: one file, one job. sound.js knows nothing about sign-in, and tictactoe.js knows nothing about Firebase. When something breaks, the file names tell you where to look.

    What happens on a visit

    1. The browser loads index.html, which loads css/retro.css and js/signin.js.
    2. The student types a username and PIN. signin.js asks firebase.js to log them in.
    3. On success, auth.js writes a small "session" note into the browser's sessionStorage.
    4. The page jumps to arcade.html. A tiny script at the top of that page checks for the note, and sends anyone without one back to sign in.
    5. The student clicks a game card, for example tictactoe.html, which runs js/tictactoe.js.

    Running it on your computer

    You might expect to double-click index.html and play. That opens the page from a file:// address, and browsers refuse to run JavaScript modules or fetch files from file:// pages for security reasons. So the README says to start a tiny local web server instead:

    Then open http://localhost:8080.

    Two copies. The class version (with logins and maths questions) is hosted on Firebase. Your own site has a second, "free" copy in arcade/ with no logins and no questions. A Python script, build_free_arcade.py, makes it from the same files. You'll see how the two share text in a later lesson.

    QUIZ

    Which file is the first page a student sees?

    • arcade.html
    • index.html
    • js/signin.js

    index.html is the sign-in screen. arcade.html is where you land after signing in, and signin.js is a script that index.html loads.

    Why does the README tell you to run python3 -m http.server instead of double-clicking the HTML file?

    • Python makes the pages load faster.
    • The pages are written in Python.
    • Browsers block JavaScript modules and fetch on file:// pages.

    The site is plain HTML, CSS and JavaScript. Python is just a quick way to serve the files over http:// so modules and fetch are allowed.

    Where do the styles that every page shares live?

    • css/retro.css
    • A <style> block at the top of each page
    • js/ui.js

    Every page links the same stylesheet, so a colour changed once in retro.css changes everywhere.

    The Page Skeleton

    Every page in the arcade starts with the same <head>. Here is the one from index.html:

    Line by line

    • <!doctype html> tells the browser to use modern "standards mode" rules instead of old quirks.
    • lang="en" tells screen readers which voice to use and lets translators know the language.
    • charset="utf-8" lets the page show any character, like the Ö in JÖRMUNGANDR and the É in APPÉTIT.
    • The viewport meta tag matters on phones and tablets. Without it, they pretend to be a wide desktop screen and shrink the whole page. With width=device-width, the page is laid out for the real screen width.

    Loading a web font quickly

    The pixel font, Press Start 2P, comes from Google Fonts. That takes two different servers: fonts.googleapis.com sends a small CSS file, and fonts.gstatic.com sends the font itself. The two preconnect links tell the browser to start connecting to both straight away, before it has even read the CSS that needs them.

    Fonts are always downloaded in "CORS mode" (a stricter kind of request), so the preconnect to the font server needs crossorigin to match. Without it, the browser opens a connection it can't reuse.

    The display=swap at the end of the font URL means "show the text in a fallback font straight away, then swap in the pixel font when it arrives". Without it, text could be invisible while the font loads.

    Our own files

    css/retro.css is a relative path: it is looked up starting from the folder the page is in. That's why the same line works on your laptop, on Firebase and on GitHub Pages. The favicon is an SVG, so it stays sharp at any size.

    The body

    The <main> element marks the page's main content, which helps screen-reader users jump straight to it. The classes (screen, center, title, blink, panel) are all defined in retro.css. The HTML says what things are; the CSS decides how they look.

    QUIZ

    What happens on a phone if you leave out the viewport meta tag?

    • The page refuses to load.
    • The phone lays the page out like a wide desktop screen and shrinks it.
    • The fonts don't load.

    width=device-width tells mobile browsers to use the real screen width.

    Why does the fonts.gstatic.com preconnect have crossorigin?

    • It makes the font download faster on every request.
    • It's required on every <link>.
    • Fonts are fetched in CORS mode, so the early connection has to match or it can't be reused.

    The other preconnect (to fonts.googleapis.com) is for an ordinary stylesheet, so it doesn't need it.

    What does display=swap do?

    • Shows text in a fallback font until the web font arrives.
    • Swaps between light and dark mode.
    • Hides the text until the font has loaded.

    "Swap" means the text is readable straight away and changes font once Press Start 2P has downloaded.

    A Retro Theme with CSS Variables

    Custom properties

    retro.css opens by naming every colour the arcade uses:

    Names that start with two dashes are custom properties (often called CSS variables). :root is the <html> element, and custom properties are inherited, so every element on the page can use them with var(): color: var(--pink);. Change --pink once and every pink thing changes.

    --font is a font stack: if Press Start 2P hasn't loaded, the browser tries the system's monospace font instead.

    Box sizing

    By default, width only counts the content, and padding and borders are added on top. With border-box, a panel with width: 440px really is 440px wide, padding and border included. Almost every modern site starts with this rule.

    The background

    100vh is the full height of the browser window, so the gradient fills the screen even when the page is short. The radial-gradient makes a soft glow at the top that fades to the background colour. The pixel font is very wide, so the body text is only 12px, with generous line spacing to keep it readable.

    CRT scanlines with a pseudo-element

    Old arcade screens had thin dark lines across them. The arcade fakes that with one rule:

    • ::after creates an extra box inside the body with no HTML needed. It only appears if it has a content, even an empty one.
    • position: fixed; inset: 0 pins it to all four edges of the window. inset: 0 is short for top: 0; right: 0; bottom: 0; left: 0.
    • The repeating-linear-gradient paints 2px of nothing, then 1px of dark, over and over: a scanline every 3 pixels.
    • z-index: 1000 puts it on top of everything, and pointer-events: none lets clicks fall through it to the buttons underneath. Without that line, nothing on the page could be clicked.

    Game pages turn the lines off with <body class="no-scanlines"> and this rule: body.no-scanlines::after { display: none; }.

    QUIZ

    Why can every element use var(--pink) when it is only defined on :root?

    • Custom properties are global variables, like in JavaScript.
    • Custom properties are inherited, and :root is the ancestor of every element.
    • The browser copies them into every rule when it loads the page.

    They behave like color: set on a parent, they flow down to every child unless overridden.

    What would happen if you removed pointer-events: none from the scanline overlay?

    • The scanlines would disappear.
    • Nothing. It's only there for speed.
    • The overlay would catch every click, so no button on the page would work.

    The overlay covers the whole window and sits on top, so it has to let clicks pass through.

    With box-sizing: border-box, how wide is a box with width: 200px; padding: 20px; border: 4px solid?

    • 200px
    • 248px
    • 240px

    Border-box counts padding and border inside the width. Without it, the box would be 200 + 40 + 8 = 248px.

    Screens, Panels and Big Type

    A column of things: flexbox

    Every page's <main> has the class screen: a flex column whose children are centred side to side (align-items) with 24px between them (gap). In a column, align-items works across the page and justify-content works down it.

    The sign-in page adds center. The selector .screen.center (no space) means "an element with both classes". It makes the column at least as tall as the window and centres everything vertically too, so the title and form sit in the middle of the screen.

    Panels

    width: min(100%, 440px) means "440px, unless the screen is narrower, then the full width". One line replaces a media query.

    The box-shadow has no blur (the third number is 0), so it's a solid black block offset 6px right and down. Hard shadows like that are what make it look like pixel art instead of a modern app.

    The title

    clamp(28px, 9vw, 60px) picks 9% of the window's width, but never smaller than 28px or bigger than 60px. The title grows and shrinks with the screen without ever getting silly.

    text-shadow can take several shadows separated by commas. Here a cyan copy sits 4px away and a black copy 8px away, which makes the chunky 3D letters.

    Blinking text

    @keyframes describes an animation. Only the halfway point is given; the browser fills in 0% and 100% from the element's normal style. steps(1) means "jump, don't fade", so "INSERT COIN TO PLAY" snaps on and off like an old arcade cabinet instead of gently pulsing.

    QUIZ

    In a flex-direction: column container, which property centres the children vertically?

    • align-items: center
    • justify-content: center
    • text-align: center

    justify-content works along the main axis, which is vertical in a column.

    What does .screen.center select?

    • A .center element inside a .screen element.
    • An element that has both the screen and center classes.
    • Every .screen and every .center.

    No space means "the same element". A space (.screen .center) would mean "inside".

    How big is font-size: clamp(28px, 9vw, 60px) on a 1000px-wide window?

    • 28px
    • 90px
    • 60px

    9vw is 90px there, which is above the 60px maximum, so it stops at 60px.

    Course 1 · Lesson 5

    Pixel Buttons

    The base button

    Buttons don't inherit the page's font by default, so font-family is set again. text-decoration: none is there because the same class is used on links (like the Teacher link in the top bar), and links are underlined by default.

    The three shadows build a 3D bevel:

    • inset -4px -4px: a dark edge along the bottom and right, inside the button.
    • inset 4px 4px: a light edge along the top and left.
    • 4px 4px 0 #000: a hard shadow outside, like the panels.

    States

    While you hold the mouse down (:active), the button moves 2px down and right and its outside shadow shrinks by the same amount. It looks like the button is pushed into the screen. The bevel flips too: the dark edge moves to the top left.

    :focus-visible only shows when the browser thinks the outline helps, usually when someone uses the keyboard. Mouse users don't see a dashed box after every click, but keyboard users always know where they are.

    Modifier classes

    Rather than writing a whole new button for each look, the HTML stacks classes: class="btn small ghost" is a small outline button. A ghost button's "border" is really an inset shadow with no offset, which doesn't change the button's size.

    Making hidden always win

    The hidden HTML attribute hides things using the browser's built-in styles, but any display rule in your own CSS beats those. A .panel with hidden would still show, because .panel sets display: flex. This rule makes hidden mean hidden, everywhere. The JavaScript relies on that a lot: button.hidden = true.

    QUIZ

    What makes a .btn look pressed while you hold it down?

    • It moves 2px down and right, and its outside shadow shrinks to match.
    • It gets darker.
    • Its text gets smaller.

    The :active rule uses transform: translate(2px, 2px) and a 2px shadow instead of 4px.

    Why does retro.css need [hidden] { display: none !important; }?

    • Old browsers don't understand the hidden attribute.
    • Any author display rule, like .panel { display: flex }, would otherwise override hidden.
    • It makes hidden elements load faster.

    The browser's built-in [hidden] style is the weakest kind of rule, so your own CSS wins without this.

    When does :focus-visible usually show its outline?

    • Every time the button is clicked.
    • Only on touch screens.
    • When the button is reached with the keyboard.

    It's the browser's best guess about when a focus ring helps, which is mainly keyboard navigation.

    Course 1 · Lesson 6

    The Sign-in Form

    Labels that wrap their inputs

    Each <input> sits inside its <label>. That connects the two without needing for and id: clicking the word "Username" puts the cursor in the box, and a screen reader reads "Username" when the box is focused. The second label's text is wrapped in a <span> with an id so JavaScript can change it from "PIN" to "Password" later.

    Helping the keyboard and the password manager

    • autocomplete="username" and "current-password" tell password managers what each box is for.
    • autocapitalize="off" and spellcheck="false" stop phones from "fixing" a username like bluefox into Bluefox.
    • type="password" hides the PIN as dots.
    • inputmode="numeric" shows a number pad on phones and tablets, because a PIN is four digits. It only changes the keyboard; it doesn't stop letters being typed.
    • required makes the browser refuse to submit while a box is empty, with no JavaScript needed.

    Two kinds of button

    Inside a form, a button's type decides what it does. type="submit" (Press start) submits the form, which also happens when you press Enter in a box. type="button" (Play as guest) does nothing on its own; JavaScript gives it a job. If the guest button had no type, it would default to submit and try to sign in.

    The guest button starts hidden. The script shows it only if guest play is switched on in config.js.

    A status line

    <p id="signin-note" role="status"> starts empty. The script writes "Signing in..." or an error like "Wrong username or PIN." into it. role="status" makes screen readers announce the new text without moving the user's focus.

    QUIZ

    What does inputmode="numeric" do?

    • Rejects anything that isn't a number.
    • Shows a number keypad on touch screens.
    • Turns the box into a number spinner.

    It's a keyboard hint only. type="number" is the one that changes the box itself, and that would show the PIN instead of dots.

    A <button> inside a form has no type. What happens when it's clicked?

    • Nothing.
    • It submits the form.
    • It resets the form.

    Buttons in forms default to type="submit". That's why "Play as guest" says type="button".

    Why is role="status" on the note paragraph?

    • It makes the text green.
    • It stops the form submitting.
    • Screen readers announce changes to its text.

    It's a "live region": new text is read out without moving the focus away from the form.

    JavaScript Modules

    The sign-in page loads exactly one script:

    type="module" changes a lot about how the file runs:

    • It can import other files. signin.js pulls in what it needs from auth.js, config.js and firebase.js, which pull in what they need. The browser fetches the whole tree.
    • It waits for the page. Module scripts are deferred: they run after the HTML has been read, so document.getElementById("login") always finds the form.
    • It has its own scope. A const at the top of a module isn't a global. Two modules can both have a variable called form without clashing.
    • It's strict. Some sloppy old JavaScript (like using a variable you never declared) throws an error instead of quietly misbehaving.

    Export and import

    A module shares things by exporting them:

    and another module imports them by name:

    The names in the curly braces must match the exports exactly. In the browser the path must be complete: "./auth.js", with the ./ and the .js. A module can also import from a full URL, which is how firebase.js loads Firebase straight from Google's servers with no install:

    A settings file

    config.js collects the things you might want to change (allow guests? how often should the tic-tac-toe CPU blunder?) into one object. Other files read config.allowGuests instead of having true buried in their code.

    Everything in the browser is public. Anyone can open developer tools and read config.js. The Firebase settings are designed to be public; the database is protected by firestore.rules on Google's side. Never put a real secret, like a password or a private API key, in front-end code.

    QUIZ

    Why can signin.js safely call document.getElementById("login") on its first line, even though the script tag comes from the page?

    • Module scripts are deferred: they run after the whole HTML has been read.
    • getElementById waits until the element exists.
    • The form is created by the script.

    Here the tag is also at the end of the body, but even in the <head> a module would wait.

    Which import works in the browser without any build tool?

    • import { config } from "config";
    • import { config } from "./config";
    • import { config } from "./config.js";

    Browsers need a real path or URL, file extension included. Bare names like "config" only work with bundlers or import maps.

    Is it safe to put a secret API key in config.js?

    • Yes, modules have their own scope, so other sites can't read it.
    • No. Every file the browser downloads can be read by the person using it.
    • Yes, if the file is minified.

    Module scope hides names from other scripts, not from people. The Firebase config is fine to publish because the rules protect the data.

    Handling the Sign-in

    Find things once

    The script looks up every element it will touch at the top and keeps them in constants. form.querySelector(...) searches only inside the form, using a CSS attribute selector to find the submit button.

    Reacting as you type

    The input event fires on every keystroke (and on paste). The moment the username contains an @, the label switches to "Password" and the phone keyboard switches back to letters. The ? : is the ternary operator: "if isEmail, this, otherwise that".

    Taking over the submit

    Step by step:

    1. event.preventDefault() stops the browser's normal submit, which would reload the page and wipe everything. Always listen for submit on the form, not click on the button, so pressing Enter is handled too.
    2. The button is disabled so an impatient double-click can't send two logins.
    3. logIn has to talk to Firebase over the internet, which takes time. It returns a Promise. await pauses this function (not the whole page) until the answer comes back. Only an async function can use await.
    4. If logIn fails, it throws, and the code jumps straight to catch. The error's friendly message is shown, the PIN box is cleared and focused for another try, and the button comes back.

    Leaving the page

    location.replace goes to a new page and replaces the current one in the browser history. After signing in, pressing Back doesn't land on the sign-in form again. (Setting location.href would add a history entry instead.) If someone who is already signed in opens index.html, they're sent straight through.

    Friendly errors

    Firebase reports failures with codes like "auth/invalid-credential". Showing that to a student wouldn't help, so firebase.js catches it and throws a new Error with a message a person can act on:

    QUIZ

    What would happen without event.preventDefault() in onSubmit?

    • The form couldn't be submitted at all.
    • The browser would do a normal submit and reload the page before the login finished.
    • The catch block would always run.

    A form's default action is to navigate. preventDefault keeps the page in place so JavaScript can handle the login.

    Why listen for submit on the form instead of click on the Press start button?

    • Pressing Enter in a box submits the form too, and submit catches both.
    • Buttons don't have a click event.
    • It's faster.

    It also means the browser's required check runs first: the submit event only fires once both boxes are filled.

    After a successful sign-in, why does the student not see the form when they press Back?

    • The form deletes itself.
    • location.replace swapped the sign-in page out of the history.
    • The browser blocks the Back button.

    And if they did reach index.html somehow, getSession() would send them straight back to the arcade.

    Remembering Who's Playing

    sessionStorage

    Each page load starts JavaScript from scratch, so variables don't survive the jump from index.html to arcade.html. To remember something between pages, the arcade uses the browser's Web Storage:

    • localStorage keeps data until it's deleted, even after the browser closes. The arcade uses it for the mute setting.
    • sessionStorage keeps data only while the tab is open. Close the tab and it's gone.

    Sign-ins go in sessionStorage on purpose. Students share Chromebooks: closing the tab should sign them out, so the next student can't play as them.

    Storing an object

    Web Storage only holds strings, so objects are turned into JSON text first:

    • { guest = false, teacher, username } in the parameter list is destructuring with a default: the function takes one object and pulls out those three properties, using false if guest is missing.
    • JSON.stringify turns { guest: false, teacher: false, username: "bluefox" } into the text '{"guest":false,"teacher":false,"username":"bluefox"}'.
    • JSON.parse turns it back. If nothing is stored, getItem returns null, and JSON.parse(null) is null. If someone has typed rubbish into the storage, parse throws, and the catch treats it as "not signed in".

    The page guard

    Every signed-in page has this in its <head>:

    It's a plain script, not a module, and it sits in the head, so it runs before the body is drawn. Someone who isn't signed in is sent away without ever seeing a flash of the game picker.

    It is only a convenience. Anyone could set that storage key by hand in developer tools. Real protection lives in the Firebase rules, and requireSession() in auth.js also double-checks that Firebase still has a real sign-in, and ends the session if not.

    Guests and signing out

    A guest gets a session too, just one marked guest: true. Other code checks that flag to skip saving scores. Signing out removes the key and goes back to the start:

    finally runs whether logOut worked or threw, so the student always ends up on the sign-in page.

    Usernames into email addresses

    Firebase only signs people in with an email and a password of at least 6 characters. Students have a username and a 4-digit PIN. So firebase.js quietly converts them: the username BlueFox becomes bluefox@students.example.com and the PIN 1234 becomes the password pin-1234. The example.com domain is reserved and never receives mail.

    QUIZ

    Why does the arcade keep the sign-in in sessionStorage rather than localStorage?

    • sessionStorage can hold more data.
    • Closing the tab signs the student out, so the next person on a shared computer can't play as them.
    • localStorage doesn't work on Chromebooks.

    localStorage would keep them signed in for days. The mute setting, on the other hand, should stick around, so it uses localStorage.

    What does getSession() return when nobody is signed in?

    • An empty object {}
    • null
    • It throws an error.

    getItem gives null for a missing key, and JSON.parse(null) is null. Bad JSON is caught and also becomes null.

    Why is the page guard a classic script in the <head> instead of part of a module?

    • Modules can't use sessionStorage.
    • Classic scripts are more secure.
    • It runs before the body is drawn, so signed-out visitors never see the page.

    A module is deferred until the page has been read, which could flash the content first.

    The Game Picker Grid

    The top bar

    .topbar is a flex row with justify-content: space-between, which pushes the brand to the left edge and the <nav> to the right. flex-wrap: wrap lets the buttons drop onto a second line on narrow screens instead of squashing.

    Look at the attributes like data-signout and data-mute. These data attributes are hooks for JavaScript, separate from the classes that style things. The script finds the sign-out button with [data-signout], so you can restyle it freely without breaking it. Several of them start hidden and are revealed only for the right people.

    An auto-filling grid

    This one line of grid-template-columns makes the picker work on every screen size with no media queries. Read it from the inside out:

    • minmax(220px, 1fr): each column is at least 220px and at most an equal share of the space.
    • repeat(auto-fit, ...): fit as many of those columns as the width allows.

    At 960px wide that's four columns; on a phone it's one. The grid works it out.

    Cards that are links

    • The whole card is one <a>, so the picture, title and text are all clickable, and it's a single stop for keyboard users.
    • width and height on the image let the browser reserve space before the picture downloads, so the cards don't jump around as images arrive. CSS still scales it with width: 100%; height: auto.
    • alt="" marks the picture as decorative. The heading already names the game, so a screen reader doesn't need to hear about it twice.

    On hover the card lifts up and left while the shadow grows by the same 3px. The shadow stays in the same place on screen, so the card looks as if it's rising off the page. It's the opposite of the button press.

    The NEW! sticker

    The sticker is position: absolute inside a wrapper with position: relative. Absolute positioning measures from the nearest positioned ancestor, so top: -10px; right: -10px places it just over the picture's top-right corner, with transform: rotate(12deg) for the slapped-on look.

    One page, two editions

    The class site and your free copy say different things about maths. Both versions of the text are in the HTML. On the class site, retro.css hides the free text with [data-only="free"] { display: none; }. The free-arcade build script keeps only the free spans. One source file, two sites.

    QUIZ

    With repeat(auto-fit, minmax(220px, 1fr)) and a container 500px wide (no gap), how many columns are there?

    • 1
    • 2
    • 3

    Two 220px columns fit in 500px but three (660px) don't. The two then stretch to share the space, 250px each.

    Why does the card's image have width and height attributes when CSS resizes it anyway?

    • They make the image download faster.
    • They let the browser reserve the right space before the image loads, so the layout doesn't jump.
    • They're required for alt to work.

    The browser uses the ratio of the two numbers (4:3 here) to size the box early.

    Why does the script find the sign-out button with [data-signout] rather than a class?

    • Classes can't be used in querySelector.
    • Data attributes are faster.
    • It keeps JavaScript hooks separate from styling, so changing classes can't break behaviour.

    Classes are for CSS, data attributes are for scripts. Either side can change without surprising the other.

    Shared Setup and the Game List

    One list of games

    js/games.js describes every game as an object in an array:

    The picker, the teacher dashboard, the feedback form and the leaderboards all read this one list. Adding a game starts here instead of hunting through ten files. That idea, keeping facts in data rather than spreading them through code, is called a single source of truth.

    Hiding unreleased games

    • .filter keeps only the games that should be hidden: not released, and not on your own computer. On localhost you still see everything, so you can test.
    • .forEach runs once for each of those games.
    • The backtick string is a template literal: ${game.page} drops the page name into the selector, making .game-card[href="analog.html"].
    • ?.remove() is optional chaining. If querySelector finds nothing it returns null, and null.remove() would crash. ?. just skips the call instead.

    initPage: the shared top bar

    Every signed-in page calls initPage() from js/ui.js:

    It checks the session (sending signed-out visitors away), then wires up whichever top-bar buttons the page happens to have. Every lookup is allowed to find nothing, thanks to ?. and if (mute), so a page with no mute button still works.     Sounds made from numbers

    There are no sound files. Each tune is a list of notes: [frequency in Hz, start time, length in seconds]. play("win") uses the Web Audio API to create an oscillator (a tone generator) for each note, which gives that 8-bit beep. Mute is remembered in localStorage, so it stays off next week too.

    What does document.querySelector(".nope")?.remove() do when there is no .nope element?

    • Throws "Cannot read properties of null".
    • Nothing. The call is skipped because the result is null.
    • Removes the whole document.

    Why does the picker keep unreleased games visible on localhost?

    • So you can test a game on your own computer before it goes public.
    • Because localhost can't run .filter.
    • It's a bug.

    A game page starts with if (!initPage()) return;. When does it return early?

    • When the page has no mute button.
    • When there's no session and initPage has sent the visitor to sign in.
    • When the player is a guest.

    initPage returns null after redirecting. Guests do have a session, so they carry on.

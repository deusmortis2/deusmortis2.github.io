COURSE 5: TIDESONG

    Course 6 · Lesson 1

    A Canvas with Buttons on Top

    Tidesong is the biggest game in the arcade: an underwater adventure where you create a mermaid or merman, swim through ten painted ocean regions and befriend 150 sea creatures by singing to them. Have a swim first: play Tidesong on your site's free arcade. Meet a creature or two, then come back.

    A game this size can't be explained line by line, so this course picks the systems worth learning from: how the code is split up, the game loop, the world map, the creature data, the battle and its song game, saving (in the browser and in the cloud), the art, and unlocking new characters. First, the page itself.

    Two layers

    Everything inside #game-frame sits in the same box. The <canvas> fills it and shows the world: the painted region, the swimmer, the creatures in battle. Everything else in the frame is ordinary HTML positioned on top of the canvas by CSS: the Menu and Bag buttons, the touch joystick, the battle message box, full-screen overlays like the shops and the Codex, and little pop-up messages called toasts.

    Why not draw the buttons on the canvas too? A canvas is just pixels. A button drawn on it can't be reached with Tab, isn't announced by a screen reader, and needs its own code to work out whether a click landed on it. Real <button>s get all of that free, and HTML wraps long text by itself, which matters in a game with a lot of talking. So the rule is: pictures on the canvas, words and controls in HTML.

    Things to notice

    • width="960" height="540" is the size of the canvas's drawing surface, in its own pixels. CSS can show it bigger or smaller on screen; the game always draws as if the screen were 960 by 540.
    • The canvas has an aria-label. A screen reader can't see what's painted, so this one sentence tells it what the canvas is.
    • hidden on the lanes, the battle box and the overlay. They're in the page from the start, ready, and JavaScript just flips hidden off when they're needed.
    • aria-live="polite" on the battle message, so "A wild Puffle swims up!" is read out, and role="status" on the toast for the same reason.
    • data-open="menu": one click handler serves all four HUD buttons by reading which screen each one opens.
    • One script: game.js, loaded as a module. It imports everything else, as the next lesson shows.

    One page, two editions

    The controls text under the game has passages like this:

    The arcade exists in two editions: the full one for students, with maths questions, and the free one on your site, without. Rather than keep two copies of the page, the text for both is written once and a small shared script (edition.js) hides whichever data-only passages don't belong to the edition being shown.

    QUIZ

    Why are the battle choices real HTML buttons and not drawn on the canvas?

    • The canvas can't draw text.
    • Buttons can be reached by keyboard, are announced by screen readers and handle their own clicks.
    • HTML is faster to draw than a canvas.

    A canvas is only pixels. Anything you can press or read belongs in HTML, positioned over it.

    What does width="960" on the canvas set?

    • The width of its drawing surface, in the canvas's own pixels.
    • Its width on screen, which can never change.
    • The maximum width of the page.

    CSS decides how big it looks. The game's drawing code always works in a 960 by 540 space.

    What are the data-only="full" and data-only="free" spans for?

    • They load different scripts.
    • They're comments for the developer.
    • One page holds the text for both editions, and a script hides the passages that don't apply.

    Writing the text once in one page means the two editions can't drift apart.

    Course 6 · Lesson 2

    One Game, Many Modules

    The tic-tac-toe game is one file. Tidesong is about thirty-five, all in js/tidesong/, and most are under 300 lines. Each file is a module with one job:

    • game.js: the conductor. It owns the game loop and calls everyone else.
    • zones.js, creatures.js, data.js: plain data (the ten regions, the 150 creatures, songs, moves and shop items).
    • world.js, worldRender.js: what's solid, where the edges lead, and drawing the map.
    • battle.js, rhythm.js, battleView.js: the battle rules, the song mini-game, and drawing a battle.
    • state.js, cloud.js, unlocks.js: saving, syncing between computers, and which characters you can pick.
    • panels.js, input.js, menus.js, town.js: the HTML layer, the keyboard and joystick, and the screens.
    • sprite.js, pose.js, art.js and the *Atlas.js files: loading and drawing the pictures.

    The imports

    ../ reaches the arcade's shared modules (questions, sound, the top bar), the same ones tic-tac-toe uses. ./ is Tidesong's own folder. Notice which way the arrows point: game.js imports everyone, and nothing imports game.js. The data files at the bottom import almost nothing. Dependencies flowing one way is what keeps a big project understandable: you can read creatures.js without knowing anything about battles.

    The game object and game.state

    There are two kinds of information here, and keeping them apart is one of the best decisions in the game:

    • game holds things that only matter right now: which screen is showing (mode), whether a menu has the player's attention (busy), which way the swimmer faces, how far through a tail beat she is.
    • game.state is the adventure: where you are, your level, pearls, items, every creature you've befriended. This is exactly what gets saved, and loading a save just means putting a saved object back into game.state.

    If the two were mixed together, every save would be full of animation timers, and loading a save might restore a half-finished tail beat.

    Starting up

    • await outside any function. That's called top-level await, and it's only allowed in modules. The rest of the file waits until the cloud saves have arrived.
    • Promise.all starts four downloads at once and waits for all of them, which is much quicker than one after another.
    • .finally runs whether the pictures loaded or not. A missing picture shouldn't stop the game from starting; the drawing code has stand-ins.
    • .find(Boolean) finds the first save slot that isn't empty, so the region you'll most likely continue in loads first.

    QUIZ

    Which of these belongs in game.state rather than game?

    • Whether a menu is open.
    • How many pearls the player has.
    • How far through a tail beat the swimmer is.

    game.state is the adventure, the part that's saved. Pearls must survive closing the tab; a tail beat doesn't need to.

    Why can game.js use await outside a function?

    • Any script can.
    • It's loaded as a module, and modules allow top-level await.
    • Because pullSaves is special.

    The page loads it with type="module". In a classic script, top-level await is a syntax error.

    What happens if the creature pictures fail to load?

    • The game never starts.
    • An error page appears.
    • The title screen still appears, because .finally runs either way.

    .then only runs on success. .finally runs on success or failure.

    Course 6 · Lesson 3

    The Game Loop and Input

    Tic-tac-toe only changes when you click. Tidesong moves all the time: water ripples, the swimmer bobs, notes fall. So it has a game loop, a function that runs once per screen refresh, about 60 times a second:

    requestAnimationFrame

    requestAnimationFrame(loop) asks the browser to call loop just before it next paints the screen. Because loop asks again at its end, it keeps going forever. The browser passes in now, a timestamp in milliseconds, and it pauses the loop by itself when the tab is hidden, saving battery.

    dt: time since the last frame

    dt ("delta time") is how many seconds passed since the last frame: about 0.0167 on a 60Hz screen, 0.0083 on a 120Hz one. Everything that moves is multiplied by it:

    So you swim 190 pixels a second however fast the computer is. Without dt, a 120Hz screen would make you swim twice as fast. Math.min(0.05, ...) caps it: after a hiccup (or coming back to the tab) a huge dt could fling you through a wall, so no frame counts for more than a twentieth of a second.

    One loop, three modes

    game.mode decides what each frame does: swim and draw the world, run a battle, or draw a backdrop behind the title screen. Notice that updateExplore (moving) is skipped while game.busy or a panel is open, but renderExplore (drawing) never is. The world keeps shimmering behind a shop menu; you just can't swim off.

    Which way to swim

    Each held key adds its arrow to a total, and so does the touch joystick. Holding right and down gives { x: 1, y: 1 }, whose length (Math.hypot, Pythagoras) is about 1.41. Swimming along that would be 41% faster diagonally, an old bug in many games. So anything longer than 1 is divided by its length, which keeps the direction but makes the length exactly 1.

    One-off actions are different: pressing M should open the map once, not 60 times a second. Those go into a queue that the loop takes from with input.nextAction(), and event.repeat (a key held down auto-repeating) is ignored for them.

    Sliding along walls

    The new x and the new y are checked separately. Swim diagonally into a building's wall and the blocked direction stops, but the other still moves, so you slide along the wall instead of sticking to it.

    QUIZ

    Why is movement multiplied by dt?

    • To make the game slower.
    • So you move the same distance per second on fast and slow screens.
    • Because requestAnimationFrame requires it.

    Speed is in pixels per second. Times the seconds this frame took, it gives this frame's distance.

    Holding up and left, what does direction() return?

    • { x: -1, y: -1 }
    • About { x: -0.71, y: -0.71 }
    • { x: 0, y: 0 }

    The total, (-1, -1), has length 1.41, so it's divided by 1.41. Diagonal swimming is no faster than straight.

    Why are the new x and new y checked against walls one at a time?

    • It's faster than checking both.
    • So a diagonal swim into a wall slides along it instead of stopping dead.
    • Walls only run in one direction.

    If both had to be free at once, touching any wall diagonally would freeze you.

    Course 6 · Lesson 4

    Regions, Edges and the Camera

    The ocean is ten regions, each one big painted picture. Swim off the edge of one and you arrive in its neighbour. All of that is described as data in zones.js:

    Each exit is [from, to, region], where from and to are fractions along that edge. Cragspire's whole north edge leads to Fangshore, but its south edge is split: the left half leads to Pelagia and the right half to Abyssal Anchor. There's no east entry, so the east edge is a wall of current.

    The other fields drive the rest of the game: levels for wild creatures, requires and drops for the key items that open the ocean up (Lesson 10), dark for how dim it is without a lantern.

    Which edge did you cross?

    • Off the top means y < 0; off the left means x < 0.
    • along is how far along that edge you are, from 0 to 1. Dividing by the width means the same exit data works however big the picture is.
    • [side, along] = [...] is destructuring assignment: two variables set in one line.
    • ?? []: a region with no exits on that side has no list at all, so an empty one stands in.
    • t is how far along that exit you were, so arrival() can put you at the matching spot on the other region's edge.

    Back in game.js, crossEdge calls this before every move. No exit: you stay put. An exit into a region whose requires item you don't have: you stay put and get a toast explaining which item you need. Otherwise you're moved into the new region.

    The camera

    A region is far bigger than the 960 by 540 canvas, so the game draws only the window around you. camX and camY are where that window's top-left corner sits in the region:

    pos - size / 2 puts you in the middle of the screen. The Math.max/Math.min pair clamps it, so near an edge the camera stops and you swim towards the side of the screen instead of showing empty space past the picture. And if a region is smaller than the screen, the result is negative: the picture is centred with a border round it.

    Drawing then subtracts the camera: the player at region position p.x is drawn at screen position p.x - view.camX.

    QUIZ

    In Cragspire, you swim off the bottom edge 30% of the way across. Where do you go?

    • Pelagia
    • Abyssal Anchor
    • Nowhere: you're blocked.

    South exits are [0, 0.5, "pelagia"] and [0.5, 1, "abyssal"]. 0.3 is in the first, and t is 0.3 / 0.5 = 0.6 along it.

    The view is 960 wide and the region 2000 wide. You're at x = 1900. What's camX?

    • 1420
    • 1040
    • 0

    1900 - 480 = 1420, but the camera can't go past 2000 - 960 = 1040, so it's clamped to 1040.

    What does exitAt return when you're still inside the region?

    • { side: null, to: null }
    • null
    • The region you're in.

    No side was crossed, so it returns null straight away. { side, to: null } means you hit an edge with no way through.

    150 Creatures from One String

    150 creatures, each with a name, an id, a region, a rarity, an element, stats, a heart song and a liked song. Written out as objects, that would be well over a thousand lines. Instead, creatures.js stores just the parts a person chose, in one compact string:

    Fifteen creatures per region, separated by |. Everything else is worked out when the module loads:

    Parsing the table

    • split("|") chops the string into pieces, trim() removes the line breaks and spaces around each, and filter(Boolean) drops empty strings (there's one at each end).
    • row.split(" ") turns "Puffle puffer tide" into three words, destructured straight into name, body and element.
    • The position decides the rest. Math.floor(index / 15) is the region number, and index % 15 the place within it: places 0 to 5 are common, 6 to 10 uncommon, 11 to 13 rare, and 14 the region's legendary. It's the same row and column arithmetic as tic-tac-toe's board, with rows of 15.

    Random, but the same every time

    Nobody picked each creature's heart song by hand; they're random. But they must be the same random on every computer, every time, or the Codex's clues would be wrong after a reload. Math.random() can't do that. makeRng(seed) in util.js is a seeded random number generator: give it the same seed and it produces the same "random" numbers in the same order. hash() turns the text "Puffle:songs" into a number to use as the seed, so each creature gets its own sequence.

    The liked trick is worth stealing. To pick a random song that isn't the heart song, pick from one fewer, and step over the heart song if you land on or past it. Every other song is equally likely and there's no "try again" loop.

    Looking one up

    Ids start at 1 (it reads better in the Codex: "No. 1"), so the array index is one less. Stats aren't stored either: a creature's body (fish, crab, whale...) gives base numbers, and its level and rarity scale them. A save only needs to remember a creature's species and level; everything else can be rebuilt.

    QUIZ

    A creature is at index 27 in the list. Which region and rarity?

    • Region 1 (counting from 0), common
    • Region 1 (counting from 0), rare
    • Region 2, legendary

    Math.floor(27 / 15) is 1, and 27 % 15 is 12, which is between 11 and 13: rare.

    Why use makeRng(hash(...)) instead of Math.random() for heart songs?

    • It's more random.
    • A seeded generator gives the same answer on every computer and every reload.
    • Math.random() doesn't work in modules.

    Same seed, same sequence. The heart songs never need to be stored or sent anywhere.

    The pool has 5 songs and heart is 2. Which songs can liked end up as?

    • 0 to 4, including 2
    • 0 to 3
    • 0, 1, 3 or 4

    It picks 0 to 3, then 2 becomes 3 and 3 becomes 4. Every song except the heart song, each equally likely.

    Course 6 · Lesson 6

    Weighted Random Encounters

    Every 32 pixels you swim through the wild is a "step", and each step might bring a creature:

    encounterChance is 0.045, a 4.5% chance per step. No creatures in town or next to a lair (isWild), and never within 6 steps of the last battle, so you can't be ambushed the moment you swim off.

    Picking which creature

    Commons should turn up far more than rares. The trick is a weighted random choice:

    Picture every creature as a stretch of a ruler, as long as its weight. Six commons at 10, five uncommons at 4 and three rares at 1.2 make a ruler 83.6 long. Pick a random point on it (rng() * total), then walk along subtracting each creature's length until you've gone past the point. Long stretches are hit more often: each common has a 10 / 83.6 (12%) chance, each rare only 1.4%. Legendaries aren't in the pool at all; they wait in their lairs.

    • ?? pool[0] is a safety net. Rounding in decimal maths could, in theory, leave roll a hair above 0 after the last creature, and then find returns undefined.
    • The level is a whole number from low to high, both included, which is why it's high - low + 1.

    The discovery boost

    Late in a region you've befriended almost everything, and the one missing rare could take forever. So creatures you haven't befriended have their weight multiplied by a boost. Each battle against one you already have (the streak) grows it by 1.3, up to 15 times. Meet a new one and the streak goes back to 0.

    Why rng = Math.random?

    The random number generator is a parameter with Math.random as its default. The game never passes one, but a test can pass a fake that returns, say, 0.99, and then check exactly which creature comes out. You did the same thing in the Pebble Nim lab. The next lab does it again.

    QUIZ

    Pool: one common (weight 10) then one rare (weight 1.2), nothing befriended, streak 0. rng() returns 0.95. Which comes out?

    • The common
    • The rare
    • Neither: undefined

    roll is 0.95 × 11.2 = 10.64. Minus the common's 10 leaves 0.64, still above 0. Minus the rare's 1.2 goes below 0: the rare.

    Why does rollEncounter take rng as a parameter?

    • So each region can use different randomness.
    • So tests can pass a predictable fake instead of Math.random.
    • Math.random isn't available in world.js.

    The default means the game doesn't have to pass anything, and tests can control every roll.

    A region's levels are [12, 17]. Which levels can a wild creature be?

    • 12 to 16
    • 12 to 17
    • 13 to 17

    Math.floor(rng() * 6) is 0 to 5, plus 12 gives 12 to 17.

    Waiting for the Player with Promises

    A battle is a long conversation: show a message, wait, show some buttons, wait for a click, show the result, wait... Written with callbacks it would be a tangle. Tidesong writes it like a story, top to bottom:

    That works because say and choose (from panels.js) each return a Promise that only resolves when the player is done. Here's choose:

    A promise you resolve yourself

    new Promise((resolve) => { ... }) runs the function straight away and hands it resolve. The promise stays pending until someone calls resolve(value). Here nobody does until a button is clicked: each button's click handler calls resolve(opt.value), and whoever was awaiting choose(...) carries on with that value. It turns "wait for a click" into something you can await.

    • actions.replaceChildren() with no arguments empties the button row, so the old buttons can't be clicked again.
    • The first enabled button gets focus, so a keyboard player can press Enter straight away.
    • escapeHtml runs on the label because labels can include your character's name, which you typed. Putting typed text into innerHTML unescaped would let a name like <img onerror=...> run code.

    say(): a click or a timer, but only once

    A message moves on by itself after a time that grows with its length (longer messages need longer to read), or when you click or press Enter. Whichever comes first calls finish; the done flag makes any later call do nothing, and finish tidies up the other listeners. The 180ms delay before listening stops the click that chose an action from also skipping the message straight after it.

    QUIZ

    When does await choose(...) finish?

    • As soon as the buttons are shown.
    • When a button's click handler calls resolve.
    • After a timer runs out.

    The promise stays pending until resolve(opt.value) is called, and only a click does that.

    Why does say use a done flag?

    • The timer and a click could both call finish; the flag makes only the first one count.
    • Promises can't be resolved twice, so it would crash.
    • To count how many messages were shown.

    A second resolve would quietly do nothing, but the clean-up would run twice. The flag keeps it simple and safe.

    Why is opt.label passed through escapeHtml?

    • To make it uppercase.
    • Buttons can't show plain text.
    • Labels can contain player-typed text, which must never be treated as HTML.

    Escaping turns < into &lt;, so typed text is shown, never run.

    Course 6 · Lesson 8

    The Battle Loop

    With say and choose to lean on, the whole battle fits in one readable function:

    Outcomes as strings

    for (;;) loops forever; the only ways out are the returns. Each pass is one round, and playerTurn reports what happened as a short string:

    • "again": you opened a menu and pressed Back. Nothing happened, so skip the enemy's turn and ask again.
    • "acted": you did something (attacked, used an item, sang and missed). Now the wild creature takes its turn.
    • "acted-first": the creature was faster, so it already struck before your attack. It doesn't get a second go.
    • "caught", "fled", "blackout": the battle is over, straight away.

    And runBattle itself resolves with "caught", "won", "fled" or "blackout", so game.js knows whether to send you back to town.

    The battle doesn't know about the page

    Look at the first argument, env. game.js builds it:

    battle.js never touches document. Everything it needs (talking, asking, sound, the song game) is handed to it. This is called dependency injection, and it's the same idea as rng = Math.random on a bigger scale: the battle rules could be run with a fake choose that always picks "Fight", to test them without a browser. { ...env, fighter, participants } copies those tools into a battle object b and adds this battle's own bits.

    Damage, and a kindness

    You fight a creature to weaken it, then sing to befriend it. If one lucky hit could knock it out from full health, you'd lose the chance to befriend it before you'd even started. So from full HP, the lowest a hit can leave anyone is 1. Math.max(1, hp - amount) then; otherwise Math.max(0, ...).

    QUIZ

    You open Fight, then press Back. What does playerTurn return, and what happens?

    • "acted": the enemy takes its turn.
    • "again": the loop skips the enemy and asks you again.
    • "fled": the battle ends.

    Backing out of a menu shouldn't cost you a turn, so continue goes straight back to your choice.

    Why is env passed into runBattle rather than battle.js importing the panels itself?

    • Imports don't work for functions.
    • The battle rules don't depend on the page, so they could run with fake tools, for example in a test.
    • It makes battles faster.

    That's dependency injection: hand a piece of code its tools rather than having it reach for them.

    A creature has 40 of 40 HP and takes a 55-damage hit. What's left?

    • 0
    • 1
    • -15

    It was at full HP, so the floor is 1: Math.max(1, 40 - 55) is 1. The next hit can finish it.

    Course 6 · Lesson 9

    The Song and Dance Game

    Choose Sing / Dance and notes fall down four lanes; press the matching arrow as each reaches its circle. A song is just data:

    notes lists the lanes in order (0 left, 1 down, 2 up, 3 right) and tempo is notes per second.

    When each note is due

    At 2.2 notes a second, the gap between notes is 1 / 2.2, about 0.45 seconds. After a one-second lead-in to get ready, note i is due at 1 + i × 0.45 seconds. Rarer creatures pass a speed above 1 (a legendary plays 25% faster), which shrinks the gap. Every note starts with hit: null, meaning "not judged yet".

    Judging a press

    • Each press carries its own timestamp, taken in the keydown handler with performance.now(). If presses were judged by the frame they were noticed in, a slow computer would make you late through no fault of your own.
    • A press matches the first unjudged note in its lane within 0.16 seconds. Within 0.075 it's perfect, otherwise good. A press near nothing is simply ignored.
    • Misses are notes that are now more than 0.16 seconds overdue and were never hit.
    • It returns true once the song has ended, which the loop uses to finish up.

    Scoring

    From the loop back to async code

    The song runs inside the game loop (Lesson 3 showed updateRhythm being called every frame), but the battle wants to write const score = await b.playRhythm(song, speed). game.js joins the two with the same "resolve it later" trick as choose:

    The promise's resolve is tucked inside rhythmDone, and the loop calls rhythmDone() when updateRhythm says the song is over. The battle code never needs to know there's a loop at all.

    QUIZ

    A note is due at 2.00 seconds and you press its lane at 2.10. What's the result?

    • Perfect
    • Good
    • Miss

    0.10 seconds off is outside the 0.075 perfect window but inside the 0.16 good window.

    Four notes: perfect, perfect, good, miss. What does rhythmScore return?

    • 0.75
    • 0.65
    • 0.5

    (1 + 1 + 0.6 + 0) / 4 = 2.6 / 4 = 0.65.

    Why does each key press store performance.now() when it happens?

    • To count how many keys were pressed.
    • So presses are judged by when you pressed, not by when the next frame noticed.
    • Because keydown events have no time.

    Frames can be 16ms or more apart. Timing each press itself keeps the judging fair on slow machines.

    Course 6 · Lesson 10

    Befriending, Keys and the Question Gate

    Did the song work?

    The chance is several factors multiplied together, each saying one thing:

    • catchRates: rarer creatures start harder (common 0.5, legendary 0.1).
    • The song: the heart song multiplies by 2.6, a liked one by 1.35, any other by 0.45.
    • perf: playing well helps, from 0.35 (all missed) up to 1.2 (all perfect).
    • hpFactor: 0.5 at full health, up to 1.5 when nearly worn out. That's why you fight first.
    • state.charm: a charm item from your bag.

    clamp(value, 0.02, 0.96) keeps the result between 2% and 96%: never hopeless, never certain. Except one case is made certain on purpose: a flawless heart song. Skill always wins. learnReaction writes down what you've learned, so next time the Sing menu shows "heart song!" beside it.

    Into the team

    state.caught is a list of species ids: which kinds you've befriended, for the Codex and the goal of 150. state.party and state.storage hold the actual creatures, each with its own level and HP. Your team holds four; extras swim off to the Tide Pool in town. stampGoal records your play time the first time caught reaches 150, for the leaderboard.

    Legendaries hold the keys

    Remember requires and drops in each region's data? Cragspire requires a Storm Charm to enter and its legendary drops a Heat Ward, which is what Abyssal Anchor requires. Beating or befriending each legendary opens the next region. The whole order of the adventure is in the data, and two short functions enforce it:

    The maths question gate

    Like tic-tac-toe, every battle ends with a question that must be answered correctly before you can carry on. Tidesong wraps it in a small ask function with one extra rule:

    Tic-tac-toe refuses to start without questions. Tidesong can't do that: you might be halfway through a long adventure. So if the question bank fails to load, questionsReady becomes false, the page says so honestly, and the game carries on without questions rather than trapping you after every battle.

    QUIZ

    Why does fighting a creature before singing make it easier to befriend?

    • Fighting teaches you its heart song.
    • hpFactor rises as its HP falls, multiplying the chance.
    • Worn-out creatures can't flee.

    1.5 - hp / maxHp is 0.5 at full HP and nearly 1.5 when it's almost worn out: three times the chance.

    A legendary hears a song it likes, but not its heart song. What happens?

    • A lower chance than with the heart song.
    • The usual liked-song chance.
    • It fails straight away: legendaries only answer their heart song.

    The legendary && reaction !== "heart" check returns "failed" before any chance is worked out.

    What happens if the question bank can't be loaded?

    • The game won't start.
    • You're stuck after your first battle.
    • A message explains it, and ask lets you carry on without a question.

    .catch turns the failure into false, and ask returns straight away when it sees that.

    Saving and Loading

    An adventure lasts weeks, so saving has to be rock solid. Saves live in localStorage, which (unlike the sessionStorage the arcade's sign-in uses) survives closing the browser. Each login gets three save slots:

    So "tidesong:save:ada", "tidesong:save:ada:2" and "tidesong:save:ada:3". When slots were added, slot 1 kept the old key, and everyone's existing adventure simply appeared in it.

    A new adventure

    The whole adventure is one plain object of strings, numbers, arrays and objects. That's deliberate: JSON.stringify can turn it into text and JSON.parse can turn it back, so saving is one line. (Creatures in the party store just their species id and level, not the species object, for the same reason.)

    When does it save?

    save() in game.js runs after every battle, after closing any menu or shop, every 20 seconds while swimming, and whenever the page is about to go away:

    beforeunload is unreliable on phones and Chromebooks, which often just freeze a tab. visibilitychange to hidden fires when you switch tabs or close the lid, so the two together catch nearly every way of leaving.

    Stamping the time

    Every save records savedAt, the time it last changed. The next lesson relies on it to decide which copy of a save is newest. But play time ticks every frame, so comparing whole saves would always find a change. saveContent uses rest destructuring: playSeconds and savedAt are pulled out into their own variables, and ...rest collects everything else. Comparing the rests answers "has anything that matters changed?".

    localStorage.setItem is wrapped in try because it can throw: storage can be full, or blocked in a private window. A save failing must never crash the game.

    Loading old saves safely

    The game has changed many times since the first saves were made, and an old save must still load. Two techniques do it:

    • Migrations. Each save carries a version. migrations[1] upgrades a version 1 save to version 2 (when the regions were repainted, it moved you back to a town). The while loop runs one step after another until the save is current, however old it is.
    • Defaults underneath. { ...fresh, ...raw } starts with a brand-new adventure and lays the saved one on top. Later spreads win, so anything the save has is kept, and any field added to the game since the save was made gets its default.

    After that, loadGame checks everything it can't trust: creatures with unknown species are dropped, items that no longer exist are removed, a position past a region's edge sends you to town.

    QUIZ

    Why does Tidesong use localStorage rather than sessionStorage?

    • It's faster.
    • It keeps the save after the browser is closed.
    • It's shared between computers.

    sessionStorage is cleared when the tab closes. Neither is shared between computers; that's what the cloud copy in the next lesson is for.

    A save from before playSeconds existed is loaded. What does { ...fresh, ...raw } give for it?

    • undefined
    • The default from newState, because raw has nothing to override it.
    • An error.

    Spreading copies fresh's fields first. raw only replaces the ones it actually has.

    You only swam on the spot for a minute, so just playSeconds changed. Does savedAt change?

    • Yes, every save updates it.
    • No: saveContent leaves play time out of the comparison.
    • Only if a minute has passed.

    Nothing that matters changed, so the old savedAt stays and the save won't look newer than it is.

    Course 6 · Lesson 12

    Cloud Sync: the Newest Save Wins

    Students play at school on one Chromebook and at home on another. A save only in localStorage would stay on the first. cloud.js keeps a copy of each slot in Firestore (Google's online database), but the game still always plays from the copy in the browser. Syncing just makes sure that copy is the newest one.

    What a slot looks like

    Tombstones

    Here's the problem with simply removing a deleted save. You delete slot 2 at home. Next day at school, the school computer still has the old slot 2, and finds the cloud has nothing for it. "Only I have this save," it thinks, "better upload it." The deleted adventure is back.

    So deleting doesn't remove anything. It writes a tombstone: { deletedAt: 1764072000000 }, a note saying "this slot was emptied at this time". A tombstone has a time like any save, so it can win or lose against the other copies in the same way.

    Merging one slot

    The rule is the copy saved last wins, and nothing else. A missing copy counts as time -1, older than anything.

    • Cloud newer: write it into this browser.
    • This browser newer (you played offline, say): send it up.
    • Same time: they're the same save. Do nothing.

    Tombstones need no special case. A deletion at 10:00 beats a save from 09:00, and an adventure saved at 11:00 (after you started a new character in that slot) beats the deletion.

    Not waiting forever

    Promise.race settles as soon as the first promise does. If the cloud answers within 6 seconds, great. If not, the timeout wins and the title screen appears using what's in the browser. But the download carries on in the background, so late tells it: you're too late to replace anything here (the player may already be playing that slot), but you may still upload this browser's newer copies.

    One more detail: pushed[slot] remembers the content last sent for each slot, so pushSlot (called after every save) doesn't upload the same save again every 20 seconds.

    QUIZ

    Why does deleting a save write { deletedAt } instead of removing the key?

    • Removing keys from localStorage isn't allowed.
    • So another computer's older copy can't bring the deleted save back.
    • To keep a backup of the adventure.

    A missing save looks like "never had one". A tombstone says "emptied at this time", which beats any older copy.

    This browser's slot was saved at time 500. The cloud's copy is a tombstone from time 800. What happens?

    • This browser's save is uploaded.
    • The tombstone is written here: the slot is deleted on this computer too.
    • Both are kept.

    800 is newer than 500, and a tombstone is just a copy with a time, so it wins like any other.

    What does Promise.race([pull(...), timeout]) wait for?

    • Both promises.
    • Whichever settles first.
    • Only the timeout.

    That caps the wait at 6 seconds on a slow or dropped connection.

    Course 6 · Lesson 13

    Atlases, Caches and Poses

    One picture, fifteen creatures

    Downloading 150 separate creature pictures would mean 150 requests. Instead each region's fifteen are packed into one image, an atlas (or sprite sheet), and a generated file says where each one is:

    "Do not edit by hand" matters: a tool cut the pictures out of the artwork and wrote this file. Fix the tool's input and run it again, or your edit disappears next time.

    Cutting one out, once

    • The nine-argument drawImage copies a part of an image: the source rectangle sx, sy, sw, sh in the atlas, drawn into the rectangle x, y, w, h on the canvas.
    • Math.min(size / sw, size / sh) is the largest scale that fits both ways, so tall and wide creatures both fit the square without stretching. size - h stands it on the bottom edge.
    • The silhouette for creatures you haven't seen: "source-in" means "paint only where there's already something", so filling the whole square with dark blue colours just the creature's shape.
    • A cache, keyed by everything that changes the result. The cutting happens once; every later frame draws the ready-made canvas. A blank canvas returned while the atlas is still loading is deliberately not cached, or the creature would stay blank forever.

    Busting the browser's cache

    Browsers keep images they've downloaded. If an atlas is redrawn but the browser keeps the old picture while the rectangles are new, every creature is cut out wrong. ?v=c906772ae3 is a hash of the picture: change the picture and the address changes, so the browser has to fetch the new one.

    Poses: animating with numbers

    The swimmer is drawn from a handful of hand-painted pictures (side view, front view, tail up, tail down), but the state of the animation is just three numbers between 0 and 1. approach moves a number towards its goal by at most one step without overshooting, so turning round takes turnTime (0.36 seconds) whatever the frame rate. Change your mind halfway and it just runs back. % 1 wraps the tail beat round from 1 to 0 forever. The drawing code then reads the numbers and picks (or blends) the pictures to show.

    QUIZ

    A creature's picture is 200 wide and 100 tall. What's its scale in a 120 square?

    • 1.2
    • 0.6
    • 0.83

    Math.min(120 / 200, 120 / 100) = Math.min(0.6, 1.2) = 0.6. It's drawn 120 by 60, standing on the bottom.

    Why isn't the blank canvas cached while the atlas is loading?

    • Otherwise the blank would be returned forever, even once the picture had loaded.
    • Blank canvases can't be stored in a Map.
    • To save memory.

    The cache is only for finished results. Next frame it tries again, and once the atlas is ready the real picture is cached.

    approach(0.9, 1, 0.25) returns...

    • 1.15
    • 1
    • 0.65

    0.9 + 0.25 would overshoot, so Math.min(goal, ...) stops it at exactly 1.

    Course 6 · Lesson 14

    Unlocking New Merfolk

    There are 12 mermaids and 12 mermen, but only three of each to choose from at first. Befriending 25, 50 and 75 creatures opens three more of each. Unlocks belong to your login, not to one adventure, so starting a new character keeps them.

    The login's tier is how many steps it has reached, 0 to 3, stored under its own localStorage key. Tier 0 gives 3 characters, tier 1 gives 6, tier 3 gives all 12. unlockOrder (in cast.js) lists the characters in the order they open, so slice(0, count) is the list you can pick from.

    Reaching a step

    Two counters are in play. state.unlockStep is how many steps this adventure has passed, saved with it. The login's tier is the best any adventure has reached. Your second character reaching 25 doesn't unlock anything new (fresh is false), but it's still a milestone, so the game still offers a change of look.

    The check lives in save() because every way of befriending a creature ends with a save. But the offer isn't shown there: you might be mid-battle. It's parked in game.lookOffer, and the loop picks it up once you're free to swim. That's a handy pattern: notice something now, act on it when the moment is right.

    Syncing unlocks: a different rule

    Saves sync by "newest wins" because an adventure can go any way, including being deleted. Unlocks can only ever grow, so the safest merge is simply the bigger number wins. It needs no timestamps at all, and no order of syncing can ever take an unlock away. Choosing the merge rule to fit the data is the real lesson here.

    The whole build, in one sentence: one page lays HTML controls over a canvas, a loop moves and draws by dt, data files describe the ocean and its 150 creatures, promises let battles read like a story, and a save is one plain object that's stamped, migrated and synced so an adventure can last for weeks on any computer.

    QUIZ

    A login is at tier 2. How many mermaids can it choose from?

    • 6
    • 9
    • 12

    Math.min(12, 3 * (1 + 2)) = 9.

    Why is the look offer stored in game.lookOffer instead of shown inside save()?

    • save() can't open panels.
    • save() may run mid-battle or in a menu; the loop shows the offer once you're free.
    • So it's saved with the adventure.

    Noticing and acting are split: save() notices, the loop acts when nothing else needs the screen.

    Why do unlocks sync by "higher wins" when saves use "newest wins"?

    • Unlocks have no timestamps because they're older code.
    • Unlocks only ever go up, so the higher count is always right, whatever order things sync in.
    • Firestore can only store the higher number.

    A save can change in any direction, even be deleted, so it needs time to decide. A count that only grows just needs max.

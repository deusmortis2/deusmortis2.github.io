COURSE 6: SPIRECLASH

    Course 7 · Lesson 1

    The Game Page

    Spireclash is the biggest game in the arcade: a 3D duel in a warded arena where two knights shoot water and fire at each other and conjure stone walls, stairs, floors and spires to win the high ground. Have a go first: play Spireclash on your site's free arcade. Then look at the page that holds it all, spireclash/index.html. Trimmed down, the body looks like this:

    Things to notice

    • #game is empty. The 3D world is drawn on a <canvas> that three.js creates and game.js puts inside it.
    • The HUD is plain HTML. The crosshair, the scores, the health bars and the hotbar are ordinary elements laid over the canvas with position: fixed. Text and bars are far easier to style in CSS than to draw in 3D. #hud has pointer-events: none so clicks go straight through it to the game.
    • Every screen is already on the page. The menu, the pause card and the results card are overlays. Switching screens just adds or removes the class hidden, which the stylesheet defines as display: none !important.
    • The crosshair is five empty tags. Four <i> ticks and a <b> dot, positioned by CSS around the centre of the screen. No images needed.
    • The scripts come last, so every element exists by the time the code looks for it.

    Thirty-six scripts and one namespace

    The other games in the arcade use JavaScript modules. Spireclash mostly doesn't: it's a long list of classic scripts that run one after another, in the order they're listed. They share their work through a single global object called G. Here's how the first one starts:

    • (function () { ... })(); is an IIFE, an Immediately Invoked Function Expression. It defines a function and calls it straight away. Anything declared inside with const or let stays private to that file, so two files can both have a helper called canvas without clashing.
    • window.G = window.G || {} means "use the G that's already there, or make an empty one". Whichever file runs first creates it; the rest add to it.
    • What a file wants to share, it hangs on G: G.combat, G.builds, G.aimAssist, G.AIBrain and so on. Later files read them back.
    • 'use strict' turns on JavaScript's stricter rules, so mistakes like assigning to an undeclared variable throw an error instead of quietly creating a global.

    Why not modules?

    The comment says it: the game was written to run "straight from file://". Browsers refuse to load type="module" scripts from a file on your disk (they need a web server), but classic scripts load anywhere. The price is that order matters. game.js uses almost everything else, so it's near the end. Move it to the top and it would crash looking for G.combat before combat.js had run.

    The one exception is quiz.js. It needs to import the arcade's shared question code, which is written as modules, so it's a module itself. You'll see in the last lesson how it passes its work to the rest of the game through G as well.

    QUIZ

    Why does the HTML leave #game empty?

    • So the page loads faster.
    • three.js creates the canvas, and game.js adds it to #game.
    • The game is drawn straight onto the page background.

    The renderer makes its own <canvas>; the page only provides somewhere to put it.

    What does window.G = window.G || {} do?

    • Always replaces G with an empty object.
    • Keeps the existing G if there is one, otherwise creates an empty object.
    • Makes G private to core.js.

    || gives the left side if it's truthy. An object is truthy, so an existing G is kept and every file adds to the same one.

    What would happen if game.js were listed before combat.js?

    • Nothing. Scripts can be in any order.
    • The browser would sort them automatically.
    • It would fail, because G.combat wouldn't exist yet when game.js ran.

    Classic scripts run in the order they appear, and each one can only use what earlier ones have already put on G.

    Course 7 · Lesson 2

    A 3D Scene with three.js

    Drawing 3D by hand means talking to the graphics card through WebGL, which takes hundreds of lines just to show one triangle. Spireclash uses three.js, a library that does that work for you. lib/three.min.js is the first script on the page and gives every other file a global called THREE.

    Every three.js program needs the same three things: a scene, a camera and a renderer.

    The renderer

    The renderer turns the scene into pixels. renderer.domElement is the canvas it draws on, and that's what lands in #game. ($ here is just a short name for document.getElementById.)

    The pixel ratio line is a speed trick. A "retina" screen has 2 real pixels for every CSS pixel in each direction, so drawing at full sharpness means 4 times the pixels. The Classic setting draws at 1 pixel per CSS pixel to keep slower laptops and tablets smooth.

    The camera

    new THREE.PerspectiveCamera(72, aspect, 0.1, 2000) takes four numbers:

    • 72: the field of view, in degrees, from the top of the screen to the bottom. Wider shows more but makes things look further away. Aiming down sights narrows it to 50 to zoom in.
    • aspect: the screen's width divided by its height, so circles stay round.
    • 0.1 and 2000: the near and far limits. Anything closer than 0.1 units or further than 2000 isn't drawn.

    The aspect has to follow the window, or the picture would stretch:

    The scene and its meshes

    The scene is a tree of everything in the world. G.createWorld() fills it with sky, ground, castle and trees. Things you can see are meshes: a shape (the geometry) plus what its surface looks like (the material). The little flash when you fire is a good small example:

    A small sphere, a glowing colour (AdditiveBlending adds its colour to what's behind it, like light), placed at the weapon's tip. add puts it in the scene for 0.07 seconds; each frame the step function fades it out and grows it a little, then it's removed.

    Units and directions

    three.js uses x for left and right, y for up and z for towards and away from the default camera. Spireclash treats one unit as about a metre: a knight is 1.8 tall, one building cell is G.CELL = 4 wide, one storey is G.LEVEL_H = 4 high, and the arena runs from -G.ARENA to G.ARENA (-32 to 32) on both x and z.

    No image or sound files. Apart from three.js itself, Spireclash loads nothing. The stone, armour and rune textures are drawn onto hidden canvases with code when the page starts, and every sound is made on the spot by a tiny synthesiser built on the Web Audio API in core.js.

    QUIZ

    Which three objects does every three.js program need?

    • A canvas, a mesh and a texture.
    • A scene, a camera and a renderer.
    • A geometry, a material and a light.

    The renderer draws the scene as seen by the camera: renderer.render(scene, camera).

    Why does the resize handler set camera.aspect?

    • To change the field of view.
    • So the picture isn't squashed or stretched when the window changes shape.
    • To make the canvas load faster.

    The aspect ratio must match the canvas. After changing it, updateProjectionMatrix() makes the camera use the new value.

    What two parts make up a THREE.Mesh?

    • A position and a colour.
    • A camera and a scene.
    • A geometry (its shape) and a material (how its surface looks).

    new THREE.Mesh(flashGeo, mat): one shape can be shared by many meshes with different materials.

    Course 7 · Lesson 3

    The Game Loop

    Tic-tac-toe only had to do something when you clicked. An action game has to move, aim, shoot and draw about sixty times a second whether you touch anything or not. That's the job of the game loop, at the bottom of game.js:

    requestAnimationFrame

    requestAnimationFrame(frame) asks the browser to call frame just before it next paints the screen. Because frame asks again on its first line, it runs once per screen refresh, forever: usually 60 times a second, more on fast monitors. The browser passes in now, the time in milliseconds.

    dt: how long since last time

    dt ("delta time") is the time since the previous frame, in seconds. Everything that moves is multiplied by it. A knight walking at 6.4 units a second moves 6.4 * dt each frame: about 0.107 at 60 frames a second, about 0.053 at 120. Either way, that's 6.4 units every second, so the game plays at the same speed on every screen.

    Math.min(0.05, ...) caps it. Switch to another tab and the browser stops calling frame; come back ten seconds later and the next dt would be 10. A knight would move 64 units in one step, straight through a wall. Capping it at 0.05 means the game simply pauses while you're away.

    One step of the world

    Each system gets its turn, in a fixed order: you, then the rival's brain, then weapon timers, then the building pieces, then effects, then animation. G.now is the game's own clock; it only moves while the game is simulating, so pausing really does freeze time.

    A state machine

    The variable state is a string that says which part of the game you're in. Each state allows different things, and the code moves from one to the next:

    1. 'menu': the rival picker. Nothing is simulated; the camera slowly circles the arena.
    2. 'countdown': 3, 2, 1. The world runs but nobody can act.
    3. 'playing': the fight. canAct is only true here.
    4. 'roundEnd': the result banner shows for 3.2 seconds.
    5. 'question': maths questions between rounds. Then back to 'countdown', or on to...
    6. 'matchEnd': the results card.

    'paused' can interrupt any of the middle ones. It saves the state it interrupted in prevState so Resume can put it back. While paused, frame still draws (so the screen isn't blank) but skips simulate.

    Timers that count down

    The countdown shows how a timer and a state change work together:

    countdownT starts at 3 and loses dt every frame. Math.ceil rounds up, so 2.7 shows as 3 and 0.2 as 1. lastCount remembers the number already shown, so the banner and beep happen once per number rather than sixty times a second. When the timer runs out, the state changes. Almost every timer in the game (reloads, cooldowns, the round clock) is this same pattern: a number of seconds, minus dt, checked against zero.

    QUIZ

    A frame arrives 16 milliseconds after the last. What is dt?

    • 16
    • 0.016
    • 0.05

    Milliseconds divided by 1000 gives seconds, and 0.016 is below the 0.05 cap.

    Why is dt capped at 0.05?

    • To make the game run at 20 frames a second.
    • After a long gap (like a hidden tab), one giant step could carry things through walls.
    • Because requestAnimationFrame can't go slower.

    A capped step is small enough to be safe. The game loses the missing time instead of leaping through it.

    Why does the countdown keep lastCount?

    • So each number's banner and beep happen once, not every frame.
    • To count how many rounds have been played.
    • Because Math.ceil needs it.

    n stays 3 for about sixty frames. Only the frame where it changes should beep.

    Course 7 · Lesson 4

    Angles: Yaw and Pitch

    Where you're looking is stored as two angles in the ctrl object: yaw (turning left and right) and pitch (looking up and down). Angles in code are almost always in radians: a full turn is 2 * Math.PI (about 6.28), a half turn is Math.PI, and a right angle is Math.PI / 2 (about 1.57).

    From an angle to a direction

    Math.sin and Math.cos turn an angle into a point on a circle of radius 1. With yaw 0, forward is { x: -0, z: -1 }: straight down the -z axis, which is where a three.js camera looks before it's turned. Turn a quarter left (Math.PI / 2) and forward becomes { x: -1, z: 0 }. The minus signs are just there to match that camera.

    Math.atan2(y, x) goes the other way: give it a direction and it returns the angle. It's the go-to tool for "which way is the rival from me?":

    Subtract your position from theirs to get the direction from you to them, then atan2 turns it into a yaw. Unlike plain Math.atan, atan2 looks at both signs, so it can tell "ahead and left" from "behind and right".

    Adding pitch

    Looking up, more of your gaze goes upwards and less goes forwards. Math.sin(pitch) is the upward part. The flat forward part is shrunk by Math.cos(pitch), so the whole direction still has length 1. Look straight up (pitch π/2) and cp is 0: all up, no forward.

    That's why pitch is always clamped: G.clamp(ctrl.pitch, -1.45, 1.45). 1.45 is just under π/2 (1.571), so you can look nearly straight up or down but never tip over backwards and see the world upside down.

    The shortest way round

    Angles wrap around. Facing 3.1 and wanting to face -3.1, plain subtraction says turn by -6.2, nearly a full circle the long way. But 3.1 and -3.1 are only about 0.08 apart, across the "back" of the circle. angleDiff always gives the short turn, between -π and π:

    • % (Math.PI * 2) removes whole turns. (In JavaScript, % keeps the sign of the left side, so the result is anywhere from -2π to 2π.)
    • More than half a turn one way is the same as less than half a turn the other way, so it adds or subtracts one whole turn.

    The aim assist and the rival's aiming both depend on this. Without it, a rival tracking you across that seam would spin all the way round.

    Easing helpers

    • lerp ("linear interpolation") finds the point a share t of the way from a to b. lerp(10, 20, 0.25) is 12.5.
    • moveTowards steps towards a target by at most maxDelta, and lands exactly on it rather than overshooting. Speeding up and slowing down use it.

    Putting it to work: the camera

    The third-person camera sits behind your right shoulder. Trimmed from updateCamera:

    Start at the knight's head (pivot), go 3.4 units backwards along the look direction, then 0.8 units to the right (the right direction is forward turned a quarter turn). Then point the camera with the same yaw and pitch. 'YXZ' says "turn by yaw first, then tilt by pitch", the order that keeps the horizon level. Aiming down sights moves the camera closer and tighter to the shoulder.

    QUIZ

    What is G.angleDiff(3.1, -3.1), roughly?

    • -6.2
    • 0.08
    • 3.1

    -6.2 is less than -π, so a whole turn (6.283) is added: about 0.083. A small turn across the back of the circle.

    Why is pitch clamped to 1.45 rather than allowed up to 2?

    • The mouse can't move that far.
    • Past π/2 (about 1.57) you'd tip over backwards and see the world upside down.
    • three.js only accepts angles below 1.5.

    Staying just short of straight up keeps the view the right way up.

    What does G.moveTowards(4, 10, 2) return?

    • 6
    • 10
    • 8

    The gap (6) is more than the step (2), so it moves 2 towards the target.

    Course 7 · Lesson 5

    Mouse Look and the Keyboard

    Capturing the mouse

    Normally the mouse pointer stops at the edge of the screen. That's no good for turning round in 3D: you'd run out of desk. The Pointer Lock API hides the pointer and reports how far the mouse moved instead, without limit.

    • Browsers only grant a lock after a click or key press, so a page can't grab your mouse uninvited. That's why clicking the canvas mid-game calls requestLock() again if the lock was lost.
    • In some browsers requestPointerLock() returns a promise that can be rejected; in older ones it returns nothing. r && r.catch handles both, and any failure shows the pause card instead of leaving you stuck.
    • Pressing Esc always releases the lock (the browser insists). The game listens for pointerlockchange and pauses, so Esc doubles as the pause key for free.

    Turning

    movementX and movementY are how many pixels the mouse moved since the last event. Multiplying by s turns pixels into radians: 0.0022 radians a pixel, times your sensitivity setting, times 0.6 while aiming down sights (so zoomed aim is steadier), times the aim assist's friction, which you'll meet in Lesson 10. Moving the mouse right gives a positive movementX, which lowers the yaw; with yaw 0 looking down -z, a lower yaw turns you to the right.

    Which keys are down?

    • keys is a lookup table of which keys are held right now. Walking doesn't happen in the key event; each frame, the movement code checks keys. That way walking is smooth and keeps going for as long as the key is down.
    • e.repeat is true for the automatic repeats you get when holding a key. One-off actions (switch weapon, drink) skip those, so holding 3 doesn't try to drink a draught thirty times.
    • The blur handler fixes a classic bug: if you hold W and Alt-Tab away, the window never sees W come back up, and you'd walk forever when you return. Losing focus lets go of everything.
    • preventDefault() stops Space scrolling the page and arrow keys moving the view mid-duel.

    Rebindable keys

    The game never checks for 'KeyW' directly. It asks keybinds.js which key is bound to each action, so players can change them from the menu:

    Bindings are stored as e.code values, which name the physical key, not the letter printed on it. On a French keyboard the key where W sits on a British one types Z, but its code is still 'KeyW', so forward stays in the same place under your fingers. And set never lets two actions share a key: give Jump the key that Wall had, and Wall takes Jump's old key.

    From keys to a wish

    Each frame, updatePlayer turns the held keys into a direction the knight wishes to go:

    Forward and right come from the yaw (Lesson 4), and each held key adds or subtracts one of them. Holding W and D together adds forward and right, which makes a diagonal of length about 1.41: you'd run 41% faster diagonally. normalize() shrinks it back to length 1. It only does that when the length is over 1, so a gentle push on the touch stick still walks slowly. Keyboard and touch both feed the same wish, so the movement code doesn't care which one you used.

    QUIZ

    Why does the game listen for blur?

    • To pause the music.
    • A key held while the window loses focus never reports its keyup, so it would stay "held" forever.
    • To save the settings.

    Clearing keys on blur means you never come back to a knight that's still running.

    Why are bindings stored as e.code rather than e.key?

    • e.key doesn't exist for letters.
    • e.code names the physical key, so WASD stays in the same place on any keyboard layout.
    • e.code is shorter.

    e.key is the character typed, which changes with the layout.

    Why is wish normalised when its length is over 1?

    • So the knight can't walk backwards.
    • To make the touch stick faster.
    • Forward plus right has length about 1.41, which would make diagonal running faster.

    Shrinking long wishes to length 1 makes every direction the same top speed.

    Course 7 · Lesson 6

    Moving a Knight

    The wish says where you'd like to go. physics() in character.js decides where you actually end up, given gravity, walls and the pieces underfoot. It runs for you and the rival alike.

    Position, velocity, acceleration

    A knight has a position (pos, where it is) and a velocity (vel, how fast it's going and which way, in units per second). Each frame, position changes by vel * dt.

    The velocity doesn't jump straight to the wish. moveTowards nudges it there by at most accel * dt. On the ground the acceleration is 55, so you reach full speed (6.4) in about a tenth of a second: snappy but not instant. In the air it's only 16, so you can steer a jump a little but not turn round in mid-air.

    Gravity and jumping

    Every frame, gravity takes 24 * dt off the upward speed. A jump sets it to a positive number (JUMP_V, about 8.6), gravity slows it to zero at the top, then it goes negative and you fall faster and faster. Math.max(-45, ...) is a terminal velocity, so a long fall never reaches silly speeds. You can only jump while onGround, so there's no jumping off thin air.

    One axis at a time

    Notice it moves along x, then separately along z. If you walk diagonally into a wall, the axis heading into the wall is blocked and its velocity set to 0, but the other axis still moves. So instead of sticking to the wall, you slide along it. This is the simplest collision trick in games, and it feels right.

    The walls and floors are axis-aligned boxes (their edges run along x, y and z), stored as { min, max } corners. Asking "would I overlap it?" is four comparisons:

    The knight counts as a square of half-width r (its radius) around (x, z). Two boxes overlap only if they overlap on both axes. If any one test fails, there's a gap between them. moveAxis also lets you walk up anything lower than G.STEP (0.6) without jumping, like a real step.

    Landing

    groundAt finds the highest surface under you: the ground (height 0), a floor, or the slope of a stair. If your feet have sunk to or below it, you've landed: snap to it, stop falling, and note how hard you hit (impact, your downward speed). game.js turns that into fall damage:

    Small drops are free. Past a speed of 17 (a drop of about a storey and a half) each extra unit of speed costs 5 health. Finally, clamp keeps both knights inside the arena's warded edge.

    QUIZ

    Why does the knight move along x and then z separately?

    • It's faster to compute.
    • A blocked axis stops while the other carries on, so you slide along walls instead of sticking.
    • three.js can only move one axis per frame.

    Walking diagonally into a wall keeps the sideways part of your movement.

    Why is the acceleration lower in the air (16) than on the ground (55)?

    • Gravity uses the rest.
    • So a jump can be steered a little but not reversed in mid-air.
    • To make jumping higher.

    Low air control makes jumps feel like they have weight.

    Two boxes overlap on x but not on z. Do they collide?

    • Yes, one axis is enough.
    • No. They only collide if they overlap on every axis.
    • Only if they're the same size.

    A gap on any one axis separates them, which is why overlapsH joins its four tests with &&.

    The Building Grid

    Building is what makes Spireclash different from a plain shooter. Every wall, floor, stair and spire snaps to an invisible grid of 4 by 4 cells, stacked in storeys 4 high. A piece is described by a small object called a spec:

    i and j are the cell's column and row (x and z), and k is the storey. To get world units, multiply: cell i starts at x = i * G.CELL. To go back the other way, divide and round down: Math.floor(x / G.CELL).

    A name for every slot

    Every slot on the grid gets a unique string, like "Wz2,-1,0". The built pieces live in a Map from key to piece, so "is something already here?" is one quick lookup: pieces.has(keyOf(spec)). No searching through a list. Stairs and spires share the S slot because both sit on a cell's slope, so you can't have both in one cell.

    A spatial hash: only look nearby

    A long duel can leave hundreds of pieces. Checking every one of them for collisions, every frame, for both knights, would be wasteful when only the few next to you matter. So pieces are also filed by the column of cells they stand in:

    This is a spatial hash: a lookup from "which square of the map" to "what's in it". Whatever the size of the build, a knight only ever checks nine columns. out is a Set because a wall on a cell edge is filed under two columns, and a Set ignores the duplicate. The last condition skips your own pieces while you've phased them with the phase wand.

    Can it go here?

    Four rules, cheapest first: the spot must be inside the arena; it must be empty; and then the piece must be supported, either standing on the ground or joined to a neighbouring piece. "Joined" works out how big the patch is where their boxes touch:

    On each axis, the overlap is "the smaller of the two ends minus the larger of the two starts". A negative overlap means a gap, so no contact. Otherwise the two biggest overlaps multiplied give the area of the touching patch. A wall resting on a floor shares a long seam and scores well; two pieces that only meet at a corner score almost nothing, and don't hold each other up. (The e lets pieces count as touching even with a hair's-width gap from rounding.)

    A piece is born weak

    A new piece starts with only 10% of its strength and builds up to full over 0.9 seconds (BUILD_TIME). It appears instantly, so building feels quick, but a wall thrown up in a panic can be shot straight back down. The material's glow is tinted blue for your pieces and red for the rival's.

    QUIZ

    Why store pieces in a Map keyed by strings like "F2,-1,1"?

    • Maps use less memory than arrays.
    • "Is this slot taken?" becomes a single lookup instead of a search.
    • So pieces are drawn in order.

    pieces.has(key) answers straight away however many pieces there are.

    Which column does x = -1 fall in, with G.CELL = 4?

    • 0
    • -1
    • -0.25

    Math.floor(-1 / 4) is Math.floor(-0.25), which rounds down to -1. (Rounding towards zero would wrongly give 0.)

    A floor four storeys up has nothing touching it. Can it be placed?

    • Yes, if it's in bounds.
    • No. It isn't on the ground and isn't joined to any piece.
    • Only by the Archmage.

    Every piece needs support, and both duellists play by the same canPlace.

    When Supports Break

    Damaging a piece

    Instead of subtracting from hp directly, a piece keeps a running total of damage taken (dmg), and hp is worked out fresh: "the strength it has reached so far, minus the damage". That's what lets a piece keep growing stronger while it's being shot. f goes from 0 to 1 over the build time, so the strength goes from 10% to 100%. The bulwark in the middle of the arena is fixed: it flashes when hit but never breaks.

    What else falls?

    Shoot out the bottom stair of a tower and everything resting on it should come down. But a piece might be held up by more than one neighbour, so you can't just knock down everything above. The real question for each piece is: is there still a chain of joined pieces from me down to the ground?

    This is a flood fill, the same idea as a paint bucket tool:

    1. Seed it with every piece touching the ground. They're all safe, so they go in reached and onto the stack of pieces still to look around.
    2. Spread. Take a piece off the stack and look at its neighbours (using the spatial hash from the last lesson). Any neighbour that's joined to it and not yet reached is safe too: mark it and push it so its neighbours get checked in turn.
    3. Stop when the stack is empty. The flood has reached everything that connects to the ground.
    4. Everything else falls.

    The !reached.has(q) check is what stops it going round in circles: a piece already reached is never pushed again, so each piece is handled once and the loop always finishes.

    Why flood from the ground?

    It might seem easier to start at the broken piece and look upwards. But "upwards" isn't simple: a floor might hang off a wall that rests on a stair that leans on something else entirely. Flooding from the ground asks one clear question of the whole build at once, and gets it right whatever shape the build is.

    Small touches

    • destroy(p, true) runs the collapse; the pieces that fall call destroy(p, false, ...), so their own removal doesn't start another flood.
    • n > 24 makes every piece after the 25th fall quietly, with no tumbling rubble. A huge tower toppling would otherwise spawn hundreds of debris effects in one frame and stutter.
    A stack or a queue? stack.pop() takes the newest item, so the flood runs deep along one branch first. Using queue.shift() would spread out evenly in rings instead. For "what's reachable?" either works, because the answer is the same set of pieces. pop is just quicker.

    QUIZ

    Why does a piece store dmg instead of just lowering hp?

    • To show damage numbers.
    • Its strength is still growing after it's placed, so hp is recalculated as "strength so far minus damage".
    • Because hp can't go below zero.

    Keeping the damage separate lets the growing strength and the damage combine correctly at any moment.

    Where does the collapse flood fill start?

    • At the piece that was destroyed.
    • At the highest piece.
    • At every piece touching the ground.

    Anything the flood can reach from the ground is supported. Everything else falls.

    What stops the flood fill looping forever when pieces join in a circle?

    • The stack has a maximum size.
    • A piece already in reached is never pushed again.
    • n > 24

    Each piece is visited at most once, so the loop must end.

    Course 7 · Lesson 9

    Hitscan Shots and Damage

    Weapons are data

    The two weapons are written as data, not code. The Water Bolt is precise and long-ranged: one pellet, tiny spread, double damage to the head. The Fire Blast is a close-range shotgun: nine pellets in a wide cone, each weak, and weaker still further away. The same firing code handles both by reading these numbers, so balancing the game means changing numbers, not rewriting functions.

    Hitscan: an instant ray

    The bolts you see flying are only effects. The hit itself is decided the instant you fire, by casting an invisible straight line (a ray) from the shooter and finding the first thing it meets. Games call this hitscan.

    • Only some meshes are tested. Each knight has two invisible cylinders, hitBody and hitHead, and each piece has one hit mesh. Testing those few simple shapes is far faster than testing every polygon of the armour. Each mesh's userData says what it belongs to, so the result can say "you hit the rival, in the head".
    • The shooter is ignored, so you never shoot yourself.
    • The ground needs no mesh. It's the flat plane y = 0. A ray that starts at height origin.y and drops dir.y per unit reaches 0 after -origin.y / dir.y units. That only works when the ray points downwards, hence the check on dir.y. Whichever is nearer, the mesh or the ground, wins.

    The same raycast answers "can I see the rival?" for the aim assist and the AI: cast towards them and see if the first hit is them.

    Spread and falloff

    Each pellet's direction is nudged by a random angle up to the weapon's spread. Running or jumping widens it, and aiming down sights passes mul = 0.45 to tighten it: standing still and aiming is rewarded.

    The Fire Blast's falloff [6, 22, 0.3] means: full damage up to 6 units away, 30% damage from 22 units on, and in between a straight line from one to the other. (d - a) / (b - a) turns the distance into "how far between 6 and 22", from 0 to 1, and lerp turns that into a multiplier. At 14 units, halfway, that's 0.65.

    Adding up the pellets

    Nine Fire Blast pellets hitting the rival shouldn't show nine little damage numbers. totals is a Map from knight to running total, so the pellets are added up first and dealt as one hit. Pieces take each pellet as it lands, which is how a shot at a wall can break the wall and carry on into the next pellet's target.

    Ward first, then health

    The ward is a magic shield on top of health. Math.min(target.ward, total) is the part the ward can soak up: all of it if the ward is big enough, otherwise whatever ward is left. The rest goes to health.

    Notice that combat.js never touches the HUD or the round score. It just calls G.events.onDamage and G.events.onDeath if they exist, and game.js fills those in to show numbers, play sounds and end the round. The combat code doesn't need to know any of that exists. These are events, or callbacks: a tidy way to let one file react to another without tangling them together.

    Can I fire yet?

    One guard line checks every reason you can't fire: dead, between shots, reloading, drinking a draught, or switching weapons. Each is a countdown timer in seconds, ticked down by combat.tick(ch, dt) every frame, just like Lesson 3's countdown. Holding the mouse button calls tryFire every frame, but fireCd makes the Water Bolt fire at most once every 0.36 seconds.

    QUIZ

    A Fire Blast pellet hits at 14 units. What share of its damage does it do?

    • 30%
    • 65%
    • 100%

    14 is halfway from 6 to 22, so the multiplier is halfway from 1 to 0.3: lerp(1, 0.3, 0.5) = 0.65.

    A knight with 20 ward and 100 health takes 34 damage. What's left?

    • 0 ward, 66 health
    • 0 ward, 86 health
    • 20 ward, 66 health

    The ward absorbs Math.min(20, 34) = 20, and the other 14 comes off health.

    Why does combat.js call G.events.onDeath instead of ending the round itself?

    • It's faster.
    • So combat doesn't need to know about rounds or the HUD; game.js decides what a death means.
    • Because modules can't end rounds.

    Callbacks keep each file to its own job.

    Aim Assist

    Tracking a moving knight with a laptop trackpad is hard. So Spireclash has aim assist, and it's on by default. The menu has a checkbox and a strength picker:

    The checked attribute ticks the box before any code runs, and the defaults in settings agree. Saved settings are copied over the defaults with Object.assign, so a player who turned it off keeps it off. Unticking the box keeps your chosen strength; assistLevel() just reports 'off' while it's unticked.

    The strengths, as data

    It does three separate things, each with its own number: pull the crosshair onto the rival, track them as they move, and add friction so your own look slows down while you're on target.

    Step 1: are you close enough?

    "Close" is measured as an angle, a cone around the line from the camera to the rival. Picture a ring of radius 2.3 units around the rival. Seen from dist away, that ring's edge is Math.atan(radius / dist) radians off centre: a right triangle with the ring's radius as the opposite side and the distance as the adjacent side. Nearby rivals get a wide cone; far ones a narrow one. Clamping stops it getting uselessly tiny far away or absurdly wide up close. Math.max(dist, 0.1) avoids dividing by zero.

    off is how far your crosshair is from the rival: the yaw gap and the pitch gap combined with Pythagoras (Math.hypot). The yaw gap is shrunk by cos(aimPitch) because, looking steeply up or down, a big change of yaw is only a small sideways movement on screen. Then two raycasts, at chest and head height, make sure no wall is in the way. Aim assist never helps you track someone behind cover.

    Step 2: how strongly?

    off / cone is 0 dead on target and 1 at the cone's edge, so 1 - off / cone goes from 1 to 0. The square root keeps the help strong for most of the cone and lets it fade only near the edge. (At halfway, Math.sqrt(0.5) is about 0.71, not 0.5.) Because it reaches 0 at the edge, the assist eases in and out smoothly instead of grabbing the view the moment you cross a line.

    Step 3: track and pull

    Tracking remembers which way the rival was last frame (prev) and turns your view by a share of how far they've moved across it since: 70% on Standard. If they strafe left, your crosshair drifts left with them. MAX_TRACK_STEP caps it, so if the rival teleports (a respawn), your view isn't yanked across the arena.

    Pulling closes a share k of the remaining gap each frame. Why 1 - Math.exp(-rate * dt) instead of simply rate * dt? Because it gives the same result however the time is sliced. Closing 10% of the gap twice leaves 0.9 × 0.9 = 81% of it; the exponential makes two frames of 0.01 seconds close exactly as much as one frame of 0.02. With plain rate * dt, a fast monitor and a slow one would pull at different strengths, and a long frame could even overshoot. This formula can never be more than 1, so it never overshoots.

    Step 4: friction

    Remember the mouse handler from Lesson 5 multiplied its sensitivity by AIM.friction(assistLevel())? On Standard, dead on target (weight 1), that's 0.65: your look moves at 65% speed, so small corrections are easier. Off target (weight 0) it's 1, full speed. With aim assist off it's always 1.

    Where it's called

    The assist changes ctrl.yaw and ctrl.pitch, the same two numbers the mouse and touch controls change. It never touches the input itself, so it works the same for a mouse, a trackpad or a thumb on a phone. It only runs while you're holding a weapon, so it never fights you when you're aiming a wall.

    QUIZ

    What happens to the cone as the rival gets further away?

    • It gets wider.
    • It gets narrower, down to MIN_CONE.
    • It stays the same.

    Math.atan(radius / dist) shrinks as dist grows: the same ring looks smaller from further away.

    Why use 1 - Math.exp(-pull * w * dt) rather than pull * w * dt?

    • It's quicker to calculate.
    • It pulls the same amount however the time is split into frames, and never goes past 1.
    • It makes the pull stronger far away.

    Frame-rate independence: 60 and 144 frames a second feel the same, and a long frame can't overshoot.

    With Standard strength and the crosshair dead on the rival, what does friction return?

    • 1
    • 0.65
    • 0.35

    1 - (1 - 0.65) * 1 = 0.65, so your look runs at 65% speed while on target.

    A Rival That Thinks

    The rival plays by exactly your rules. It's another Character with the same physics, the same tryFire, the same canPlace and the same box-in cooldown and phase wand (G.RULES in core.js). The only difference is that an AIBrain decides its wish, its aim and its builds instead of a keyboard.

    Difficulty as data

    Like the weapons, the three rivals are one brain with three sets of numbers. The Squire reacts in over half a second, aims loosely and builds slowly. The Archmage reacts in 0.14 seconds, tracks you nearly five times as fast and knows building tricks (nineties, cone) the Squire doesn't. Making a rival harder is a matter of turning dials.

    Thinking isn't every frame

    Aiming happens every frame, so it's smooth. But the big decisions (should I climb? box in? heal?) happen in think(), which only runs every p.think seconds: 0.15 for the Squire, 0.05 for the Archmage. That's cheaper, and it's more human: people don't change plans sixty times a second. think() is another state machine, with modes like 'engage', 'rampRush', 'nineties', 'box' and 'heal', and a switch that runs the plan for the current mode.

    Reaction time: seeing the past

    A computer always knows exactly where you are. A fair rival shouldn't. So the brain keeps a short history of where you've been, and aims at where you were one reaction time ago:

    • Every frame, a snapshot goes on the end of history.
    • The while loop drops snapshots off the front while the second one is already old enough. That leaves history[0] as the newest snapshot that's at least reaction seconds old: what the rival "sees".
    • Dodge left and the Squire keeps shooting where you were for over half a second. That's your chance.
    • The Archmage is predictive: it takes that old snapshot and adds your velocity times the delay, guessing where you've got to since. Run in a straight line and it'll find you; change direction and it guesses wrong.

    Aiming like a person

    • Turning uses the very same frame-rate-safe easing as the aim assist's pull: close a share 1 - exp(-track * dt) of the gap. track is how fast it swings round.
    • fireTol: it holds fire until its aim is within that many radians of where it wants to be, like a person waiting to line up the shot.
    • The wobble isn't Math.random(), which would jitter wildly from frame to frame. It's two sine waves of different speeds added together, which drifts smoothly and never quite repeats, like a slightly unsteady hand. this.seed starts each rival at a different point in the wave. amp comes from aimErr, and grows when you're moving fast.

    Building on a timer

    When think() decides to climb, it doesn't build the whole staircase at once. It pushes specs onto a queue, and processQueue places them one at a time, every buildInterval seconds (with a little randomness so it doesn't tick like a metronome). This queue is first in, first out: shift() takes the oldest. Specs that have become impossible (already built, or no longer supported) are skipped.

    QUIZ

    With reaction: 0.3, which snapshot does history[0] hold?

    • The newest one.
    • The newest snapshot that is at least 0.3 seconds old.
    • The very first one of the round.

    Older snapshots are dropped only while the next one is old enough to take their place.

    Why is the aim wobble made from sine waves rather than Math.random()?

    • Sines drift smoothly from frame to frame, like an unsteady hand; random numbers would jitter.
    • Math.random() is too slow.
    • Sines make the rival more accurate.

    Adding two sines of different speeds gives a smooth wander that doesn't obviously repeat.

    Why does think() run every p.think seconds instead of every frame?

    • It can't run faster than that.
    • Big decisions don't need to change sixty times a second; it's cheaper and feels more human.
    • So that aiming is slower.

    Aiming still updates every frame; only planning is spaced out.

    Course 7 · Lesson 12

    Rounds, Questions and the Leaderboard

    Ending a round

    A duel is first to 3 round wins (WIN_SCORE), so at most five rounds. A round ends when a knight falls (combat.js calls G.events.onDeath, which calls endRound), or when the 60-second clock runs out:

    A tie-breaker chain with early returns: compare damage dealt; if that's level, compare what's left; if that's level, it's a draw (null). Each test only runs when the one before it couldn't decide.

    The round clock: 65 seconds is Math.floor(65 / 60) = 1 minute and 65 % 60 = 5 seconds. padStart(2, '0') adds a leading zero, so it reads 1:05, not 1:5.

    The question gate

    1. Let go of everything. Clear the held keys and buttons, and release the pointer lock so you have a mouse pointer to click the answer box with. The 'question' state also makes the keydown handler ignore keys, so typing an answer doesn't swing your knight around.
    2. Ask. ROUND_TIME - roundT is how long the round lasted.
    3. Carry on once the promise resolves, but only if the game is still waiting for it. If you left for the menu meanwhile, state has changed, and starting a round would be a nasty surprise.
    4. Lock the mouse again for the countdown. That's allowed here because answering was a click.

    quiz.js: the bridge from a module

    • This is the one module in the game. It imports the arcade's shared question code (the same gameQuestions tic-tac-toe uses), then hands two functions to the classic scripts by hanging them on window.G.
    • A quick round earns one question; a long one, two. askEach asks them one after another, and each must be answered correctly before the next appears.
    • If the question bank fails to load, askRoundQuestions just returns, and the duel carries on rather than getting stuck forever.
    • Your free arcade simply leaves quiz.js out. Then G.askRoundQuestions is undefined, and the !G.askRoundQuestions check in afterRound goes straight to the next round. Same game.js, no maths.

    The leaderboard

    Each win against a rival adds one to your count for that rival on the arcade leaderboard. includes checks the name is one of the three real bots before anything is written. { [bot]: ... } is a computed key: the brackets use the value of bot as the key, so a Knight win writes { spireclash: { knight: increment(1) } }. increment(1) is a Firestore instruction meaning "add one to whatever is stored", which is safe even if two wins are saved at nearly the same moment.

    Remembering your settings

    Sensitivity, volume, rival, key bindings and aim assist are saved as one JSON string in localStorage whenever they change, and read back by core.js at start-up. The try/catch matters: in some private windows storage throws an error, and a game that crashed over a volume setting would be a poor game.

    The whole duel, in one sentence: a page of overlays over a three.js canvas, a loop that steps every system by dt, angles turned into directions, boxes that collide one axis at a time, a grid of pieces held up by a flood fill, rays that decide every hit, an aim assist and a rival built from the same smoothing maths, and a small module that asks the maths questions in between.

    QUIZ

    Time runs out. You dealt 120 damage, the rival dealt 120, and you have more health and ward left. Who wins?

    • Nobody: it's a draw.
    • You, "decided on health".
    • The rival, because it's the defender.

    Damage is level, so the next tie-breaker (health plus ward left) decides it.

    Why does afterRound release the pointer lock before asking questions?

    • So you have a visible mouse pointer to use the answer box.
    • Pointer lock stops promises resolving.

    With the pointer locked, it's hidden and stuck in the game.

    How does the free arcade skip the questions without changing game.js?

    game.js checks whether the function exists before using it.

COURSE 3: DEUS DRACONIS

    Course 3 · Lesson 1

    The Canvas and Its Coordinates

    Have a flight first: play Deus Draconis on your site's free arcade. Steer the dragon with the arrow keys, breathe fire with space, and try to reach the first wyrm.

    Tic-tac-toe was built from buttons: real HTML elements that the browser draws for you. Deus Draconis is a different kind of page. Monsters swoop, fireballs fly and the sky scrolls sixty times a second, and there's no element for any of it. Instead, the whole game is painted, pixel by pixel, onto one canvas. This course walks through all 17 files in js/draconis/ and explains how they turn into a game.

    One element to draw on

    • <canvas> is a blank rectangle of pixels. On its own it shows nothing. JavaScript draws on it.
    • width="480" height="360" is the size of the drawing: 480 by 360 pixels. CSS can still show it bigger (fullscreen stretches it right across the screen), but the game always draws as if it were 480 by 360. Everything is scaled up together.
    • aria-label matters more here than usual. A screen reader can't see anything painted on a canvas, so the label is the only description it gets.
    • #load-error is an ordinary paragraph for a message if the art or questions fail to load. Plain HTML is still the easiest way to show text that has to be read.

    The only other thing in the body that matters to the game is the script:

    Getting a pen

    getContext("2d") hands back the canvas's drawing context, which every canvas program calls ctx. Every drawing command in the game goes through it: ctx.fillRect, ctx.drawImage, ctx.fillText and friends. The canvas itself is just the paper; ctx is the pen.

    Which way is up?

    A canvas measures from its top-left corner. The point (0, 0) is the top-left pixel, x grows to the right, and y grows downwards. That's upside down compared with graphs in maths lessons, and it catches everyone out at first. The game's size and the dragon's playing area live in entities.js:

    Read dragonBounds with "y goes down" in mind: minY: 185 and maxY: 280 keep the dragon in the lower part of the screen, below the monsters. The canvas is 360 tall, so maxY: 280 leaves a strip at the bottom for the lives and fireball icons.

    Filling rectangles and writing text

    Here's the level bar from the heads-up display: a dark box with a blue bar inside it.

    The pattern is always the same: set the style, then draw. fillStyle takes any CSS colour, and fillRect(x, y, width, height) paints a rectangle whose top-left corner is at (x, y). The second bar starts one pixel in and is drawn as wide as the player's share of the XP they need, so it fills up as they level.

    Text works the same way, through a small helper every screen uses:

    • ctx.font is written exactly like the CSS font shorthand.
    • textBaseline = "top" makes y the top of the letters, so text sits where you'd expect a box to sit.
    • The text is drawn twice: once in black, nudged down and right, then in colour on top. That's a drop shadow, so the words stay readable over a bright sky or a busy fight.
    • The last parameter is an object with defaults. text(ctx, "HI", 10, 10) gets white, size-10, left-aligned text without passing anything else.
    A canvas has no memory of shapes. Once a rectangle is painted it's just coloured pixels. There's no "rectangle object" to move later. To make something move, the game paints the whole picture again, with the thing in its new place. The next lesson shows the loop that does that.

    QUIZ

    On a canvas, where is the point with y = 0?

    • Along the bottom edge.
    • Along the top edge.
    • Across the middle.

    The origin is the top-left corner, and y counts downwards. That's why the dragon, which flies low on the screen, has big y values (185 to 280).

    Fullscreen shows the canvas 960 pixels wide. What x does the game use for the right-hand edge?

    • 480, the canvas's own width.
    • 960, the size on screen.
    • It depends on the monitor.

    The width attribute sets the drawing size. CSS only stretches the finished picture, so the game's maths never changes.

    Why does text() call fillText twice?

    • The first call loads the font.
    • To make the letters bolder.
    • The first, black and nudged, is a drop shadow under the coloured text.

    Drawing the shadow first and the colour on top keeps HUD text readable over any background.

    The Game Loop

    Every action game is the same two steps, repeated as fast as the screen can refresh: update the world a little, then draw it. Each pass is one frame. The arcade's canvas games share this loop. It lives in game-shell.js, at the end of runGame:

    requestAnimationFrame

    requestAnimationFrame(frame) asks the browser: "call frame just before you next repaint the screen". It calls it once, with a timestamp in milliseconds. So frame ends by asking again, which makes a loop that runs once per screen refresh: usually 60 times a second, sometimes 120 or more on fast screens. When the tab is hidden, the browser stops calling it, so a game in a background tab costs nothing.

    Why not a while (true) loop? JavaScript runs on one thread. A loop that never stops would never give the browser a chance to show the picture or handle a key press, and the page would freeze. requestAnimationFrame does one frame, then hands control back until the next one.

    Delta time

    (now - last) / 1000 is the time since the last frame, in seconds. Games call it dt ("delta time"). On a 60 Hz screen it's about 0.0167; on a 120 Hz screen it's half that. Every speed in the game is written per second and multiplied by dt:

    dragonSpeed is 165, so the dragon covers 165 pixels in one second whether that second had 60 frames of 2.75 pixels or 120 frames of 1.375 pixels. Without dt, the game would run twice as fast on a fast screen.

    The cap

    Math.min(..., 0.05) means no step is ever longer than a twentieth of a second. Switch to another tab for ten seconds and come back: the first frame would otherwise have a dt of 10, and every monster and fireball would jump ten seconds' worth in one go, straight through the dragon. With the cap, a slow frame makes the game run slightly slower for a moment instead of teleporting. Math.max(..., 0) guards the other end, so time never runs backwards.

    Update, then draw

    update changes the game's state. draw paints it. They're kept strictly apart: the top of render.js says "Pure output: reads game state, never changes it." It's the same idea as render() in tic-tac-toe, but now it runs every frame instead of after every click.

    How Draconis plugs in

    The game hands runGame one object full of settings and functions, and runGame does the rest in order:

    1. Checks the player is signed in and sets the canvas size.
    2. Runs setup(), so there's a scene ready to draw.
    3. Waits for everything in load() at once with Promise.all: the question bank, the dragon's art, the monsters' art, and the pixel font. A canvas can only use a web font that has already downloaded, so document.fonts.load fetches it before the first frame.
    4. Runs ready(), which turns on the controls.
    5. Starts the loop, calling the game's update(dt) and draw() every frame.

    If anything fails to load, the catch in runGame writes the error into #load-error and the loop never starts. Astro Stomp and Jörmungandr use exactly the same shell, so none of the three needs a loop of its own.

    QUIZ

    Why is every speed multiplied by dt?

    • To make the numbers smaller.
    • So things move the same distance per second however many frames the screen shows.
    • requestAnimationFrame needs it.

    Speeds are "pixels per second". Multiplying by the seconds since the last frame gives the right step for that frame.

    The player comes back after 3 seconds in another tab. What dt does the next update get?

    • 3
    • 0.05
    • 0

    Math.min(3, 0.05) is 0.05. The cap stops everything jumping three seconds ahead in one frame.

    What does requestAnimationFrame(frame) do?

    • Calls frame 60 times, then stops.
    • Calls frame straight away.
    • Calls frame once, before the next repaint. frame asks again to keep the loop going.

    It's a one-off request. The loop exists because each frame requests the next.

    Course 3 · Lesson 3

    Keyboard and Pointer Input

    In tic-tac-toe, a click was the move. An action game can't work like that. When you hold the right arrow, the dragon should glide smoothly for as long as the key is down, and holding up at the same time should fly diagonally. So the game doesn't react to key presses directly. It keeps a list of the keys that are held down right now, and every frame looks at that list.

    A set of held keys

    • A Set is a collection with no duplicates. keys.add("w") twice still holds one "w", and keys.has("w") is a quick yes or no.
    • keydown adds, keyup deletes. Between the two, the key is in the set.
    • event.key.toLowerCase() turns "ArrowUp" into "arrowup" and a Caps Lock "W" into "w", so both work.
    • preventDefault() stops the browser's own reaction to these keys. Without it, space and the arrows would scroll the page while you play.
    • event.repeat is true for the automatic repeats a held key sends. One-off actions (fire, pick a card) happen on the first press only, so holding space doesn't empty your fireballs.
    • If a <dialog> is open (a maths question), keys are left alone, so typing an answer of "3" doesn't pick a power-up.
    • blur fires when the window loses focus. If you hold right and click into another window, the keyup goes to that window, not the game. Clearing the set stops the dragon flying right forever.

    Reading the set every frame

    ...names is a rest parameter: it gathers all the arguments into an array, so held("arrowup", "w") asks "is either of these down?". Then dx is "right minus left". Hold right: step - 0. Hold left: 0 - step. Hold both: step - step, which is 0, so they cancel out instead of fighting.

    Staying on screen

    Math.min(Math.max(value, low), high) is the standard clamp. Math.max lifts anything below low up to it; Math.min pulls anything above high down to it. A move to x = 500 becomes 464, and a move to x = 3 becomes 16.

    Dragging on a touch screen

    Pointer events cover mouse, finger and pen in one go. A finger's position is in screen pixels, but the game thinks in canvas pixels. If the canvas is shown 960 wide, moving your finger 10 screen pixels is only 5 canvas pixels, so scale() (480 divided by the size on screen) converts one to the other. A touch that barely moved (under 8 pixels in total) counts as a tap, which breathes fire.

    QUIZ

    The player holds both the left and right arrows. What is dx?

    • 0, so the dragon doesn't move sideways.
    • step, because right is checked first.
    • -step, because left wins.

    step - step is 0. Opposite keys cancel out.

    Why does the game clear the held keys on blur?

    • To save memory.
    • A key released while another window has focus never sends its keyup to the game.
    • So the player has to press start again.

    Without it, a key could stay "held" in the set forever, and the dragon would drift on its own.

    With dragonBounds.maxX at 464, where does moveDragon put a dragon that tries to reach x = 470?

    • 470
    • 464
    • 16

    Math.max(470, 16) is 470, then Math.min(470, 464) is 464.

    Course 3 · Lesson 4

    Game Objects as Plain Objects

    The dragon, every monster, every arrow, every explosion: each is just a plain JavaScript object with an x and a y, plus whatever else it needs. There are no classes and nothing special. A thing in the game is a bag of numbers that update changes and draw paints.

    The whole game in one object

    This is the game's whole state, the same idea as tic-tac-toe's board and score. It holds what lasts across lives: the score, the stage, how many times the dragon has died, its level and powers (progress). What happens during one life lives in game.round.

    A fresh round

    When the dragon loses a life, the game doesn't hunt down every monster and arrow to remove them. It simply builds a brand-new round and throws the old one away. Fresh empty lists, a dragon back at the start, done.

    Look at dragon: { ...dragonStart }. The spread makes a copy of the starting position. If the round used dragonStart itself, then moving the dragon would change dragonStart, and the next life would begin wherever the dragon died.

    Lists that update themselves

    Monsters, shots, fireballs and effects each live in an array. This is how the monsters and shots are moved every frame:

    It's one neat trick. updateMonster moves a monster and returns whether it should stay: true to keep it, false once it has flown off screen or finished fading. filter keeps only the ones that answered true. Moving and tidying up happen in a single line, and nothing ever builds up off screen.

    Why new shots wait in incoming

    A monster fires during its update, which runs in the middle of the loop over the monsters, and a bursting boulder fires shards in the middle of the loop over the shots. Adding to an array while filter is walking through it is asking for trouble. So spawnShots puts new shots in a waiting list, and they join the real list once all the updates are done.

    Effects with an age

    An effect (an explosion, a lightning bolt, a spark) is an object with an age that grows every frame and a life. When age passes life it's filtered away. e.life ?? 0.4 gives effects without a life a default of 0.4 seconds. When a boss falls, the game queues ten explosions with negative ages, so they go off one after another:

    The drawing code skips any effect whose age is still below 0, so explosion 5 stays invisible until 0.6 seconds have passed.

    QUIZ

    Why does newRound write dragon: { ...dragonStart }?

    • Spreading is faster than assigning.
    • It copies the start position, so moving the dragon can't change dragonStart.
    • dragonStart is a const, so it can't be used directly.

    Objects are shared by reference. Without the copy, the next life would start wherever the last one ended.

    How does a monster get removed from round.monsters?

    • The game calls splice when it dies.
    • Its update returns false, and filter leaves it out of the new list.
    • It's removed when the round ends, and not before.

    Every update both moves the thing and answers "keep me?".

    An effect has age: -0.36. When does it first appear?

    • Straight away.
    • After 0.36 seconds, when its age reaches 0.
    • Never: negative ages are filtered out.

    The filter keeps it (its age is below its life), and the drawing code skips it until its age is 0 or more.

    Course 3 · Lesson 5

    Drawing Sprites

    A sprite is a small picture that gets drawn again and again: the dragon, a goblin, a fireball. Deus Draconis gets its sprites two ways: tiny ones are written out as text in the code, and big ones are cut from the artist's picture files.

    Pixel art written as text

    Squint and you can see the fireball: a red rim (r), orange (o), a yellow-hot middle (y), and . for see-through. This little function turns the text into a picture:

    It makes a second, off-screen canvas that's never added to the page, and fills one scale-sized square per letter. palette["."] is undefined, so dots are skipped and stay transparent. The finished little canvas is the sprite: ctx.drawImage happily draws a canvas onto another canvas, just like an image. The same rows at scale 2 make the flying fireball, and at scale 3 the bigger HUD icon.

    Cutting frames from a sheet

    The dragon's art is one PNG strip holding six pictures side by side, each with the wings in a different position. The game cuts it up once, at load time:

    The cutting trick: each frame gets a canvas exactly one frame wide, and the whole strip is drawn into it shifted left by i * frameWidth. Only frame i lands inside; the rest falls off the edges. await image.decode() waits until the PNG has downloaded and is ready to draw, which is why loadDragon is one of the promises runGame waits for.

    Drawing at the centre

    drawImage(sprite, x, y) puts the sprite's top-left corner at (x, y). But the game stores every thing's centre, which makes collisions and aiming much simpler. So the drawing code subtracts half the width and height. Math.round keeps the sprite on whole pixels, so pixel art never goes blurry from being drawn half a pixel off.

    Remember pixelated: true in the last lesson? It sets ctx.imageSmoothingEnabled = false. When pixel art is drawn bigger, the browser normally blurs it smooth. With smoothing off, each pixel becomes a crisp square block.

    Flapping: animation from the clock

    flapOrder (in sprites.js) is [4, 2, 0, 5, 3, 1, 3, 5, 0, 2]: the frame numbers in the order that makes a smooth flap, wings up, level, down, folded and back. game.clock counts seconds, so Math.floor(clock * 5) goes up by one five times a second, and % flapOrder.length wraps it back to the start. No timers, no counters: the frame is worked out from the time.

    Rotating with save and restore

    A canvas can't rotate a picture directly. Instead you rotate the paper. translate moves the origin to the sprite's centre, rotate turns the paper around that point, and the sprite is drawn centred on the new origin. The axes are now twisted, so save() (before) and restore() (after) put everything back. Spinning axes and boulders use this, with the angle growing from their age.

    See-through and flashing. ctx.globalAlpha sets how solid everything drawn next is, from 0 (invisible) to 1. The dying dragon fades with ctx.globalAlpha = Math.max(0, 1 - game.phaseTime / 1.2), and a shielded dragon blinks by skipping its draw on every other tenth of a second. Always set it back to 1 afterwards, or everything else goes see-through too.

    QUIZ

    A sprite is 40 pixels wide and 30 tall. To centre it on (100, 100), where is its top-left corner drawn?

    • (100, 100)
    • (80, 85)
    • (120, 115)

    Subtract half the width (20) and half the height (15).

    At game.clock = 1, which dragon frame does flapFrame pick?

    • Frame 5
    • Frame 1
    • Frame 0

    Math.floor(1 * 5) % 10 is 5, and flapOrder[5] is 1.

    Why does drawRotated call ctx.restore() at the end?

    • To show the sprite on screen.
    • To undo the translate and rotate, so later drawing isn't moved and twisted.
    • To free the sprite's memory.

    save() remembers the context's settings and restore() brings them back.

    Collisions: Circles and Boxes

    "Did the arrow hit the dragon?" A canvas can't answer that: it only has coloured pixels. The game has to work it out from its own numbers. The trick is to pretend every thing is a simple shape and test the shapes.

    Circles

    Two circles touch when the distance between their centres is less than their two radii added together. Math.hypot(dx, dy) is Pythagoras: √(dx² + dy²), the straight-line distance. A dragon (radius 14) and a goblin (radius 20) whose centres are 30 apart are touching, because 30 is less than 34.

    Circles suit Draconis because almost everything spins, tilts and swoops, and a circle looks the same at every angle. The circles are also a bit smaller than the pictures: each dragon frame is about 100 pixels wide with its wings out, but only a 28-pixel circle round its body counts. Small, forgiving hitboxes make near misses feel fair.

    Who hits the dragon?

    • t.r ?? radius.monster: a thing with its own radius uses it (the boss's is 38); everything else counts as 20.
    • some stops at the first match. One hit is enough.
    • touchesDragon(m) skips monsters that are dead or faded out, so a skeleton that has vanished can't hurt you.

    Shots have their own check, and one of them isn't a circle at all:

    The floating eye's beam is a column of light from the eye down to the bottom of the screen. So the test is "is the dragon's x close enough to the beam's x, and is it below the eye?". Use whatever shape matches the thing.

    Fireballs that hit once

    A fireball and a monster overlap for several frames in a row while one passes through the other. Without care, a piercing fireball would hit the same orc on every one of those frames. So each fireball carries a Set called hits, and a target already in it is skipped. An ordinary fireball (no pierce) simply returns false and disappears on its first hit.

    Boxes

    Rectangles have a test too, and the game uses it for the power-up cards. "Is this tap inside a card?" is a point in a box:

    The point must be right of the left edge, left of the right edge, below the top and above the bottom. findIndex returns the card's number, or -1 for "none", which is how input.js knows a tap missed every card and should fire instead.

    Two boxes overlapping is the same idea, done for both. The ground painter uses it to keep crop fields apart (with a 6-pixel gap):

    Leave out the 6s and it reads: A's left is before B's right, and B's left is before A's right (so they overlap sideways), and the same for top and bottom. Only when both directions overlap do the boxes really overlap. This is called an axis-aligned bounding box test (AABB for short), and platform games use it everywhere, because their walls and floors are rectangles.

    QUIZ

    A fireball (radius 6) is 25 pixels from a goblin (radius 20). Do they overlap?

    • Yes: 25 is less than 26.
    • No: 25 is more than 20.
    • Only if the fireball is moving towards it.

    Compare the distance with the two radii added together: 6 + 20 = 26.

    Why does each fireball keep a hits set?

    • To count the score.
    • So a fireball passing through a foe over several frames only hits it once.
    • To remember which monsters are stone.

    Overlaps last for several frames. The set makes each hit count once.

    Box A runs from x = 0 to 10, box B from x = 10 to 20, both at the same height. With the strict < test, do they overlap?

    • Yes, they share the line x = 10.
    • No. B's left edge (10) isn't less than A's right edge (10).
    • It depends on their heights only.

    10 < 10 is false, so boxes that only touch edges don't count as overlapping.

    Stages and Spawn Schedules

    What makes the second stage different from the first? Not different code. Different data. Each stage is one object in a list, and the rest of the game reads it.

    • kinds: which monsters appear. Stage 1 has goblins, eyes and griffins; stage 3 has all six.
    • pace: how long monsters wait between attacks (smaller is faster). Stage 3's 0.85 makes everyone attack 15% more often.
    • spawnGaps: seconds between monsters at the start of the stage, and at the end.
    • scenery: which background to paint.
    • boss: everything about the wyrm, including the list of attacks it cycles through.

    Making the game harder, or adding a fourth stage, means editing this list. No other file has to change.

    Building the timetable

    Before the stage starts, the whole timetable is written out: a list like [{ at: 1.5, kind: 0 }, { at: 5.9675, kind: 4 }, ...].

    • Taking turns. order is a queue of kinds. shift() takes the first one off the front. When it's empty it's refilled, so the kinds go round and round and none can be missed out.
    • Getting faster. at / stageSeconds is how far through the stage we are, from 0 to 1. The gap slides from startGap towards endGap along the way. Halfway through stage 1 it's 4.5 + (3.2 - 4.5) × 0.5 = 3.85 seconds. Sliding from one value to another like this is called linear interpolation (or "lerp").
    • A breather. Spawning stops 5 seconds before the end, so the sky can clear before the boss arrives.

    A fair shuffle

    Stage 3 sets shuffle: true, so each round of six comes in a random order. This is the Fisher-Yates shuffle: walk backwards through the list, swapping each item with a random one at or before it. Every order is equally likely. The line [copy[i], copy[j]] = [copy[j], copy[i]] swaps two items using destructuring, with no spare variable needed.

    Spawning during play

    spawnIndex points at the next entry in the timetable. Every frame, while that entry's time has come, its monster is created and the index moves on. It's a while, not an if, so two entries due in the same frame both spawn.

    When the index runs past the end, round.spawns[round.spawnIndex] is undefined. The optional chaining ?.at turns that into undefined instead of an error, and undefined <= time is false, so the loop just stops. After 60 seconds, the boss arrives.

    QUIZ

    With spawnGaps: [4.5, 3.2], what's the gap after a monster at at = 30?

    • 4.5 seconds
    • 3.85 seconds
    • 3.2 seconds

    30 is halfway through 60, so the gap is halfway between 4.5 and 3.2.

    What stops the while loop in spawnFoes once the timetable is used up?

    • An error, caught by runGame.
    • ?.at gives undefined, and undefined <= time is false.
    • The boss deletes the timetable.

    Optional chaining stops at undefined instead of throwing.

    Why is the stage list good news for whoever balances the game?

    • It loads faster than code.
    • Difficulty, monsters and bosses can all be changed by editing data, without touching the logic.
    • Players can edit it.

    The code reads whatever the data says, so tuning is a matter of changing numbers.

    Phases and the Question Gate

    The game is always in exactly one phase: the title screen, a stage intro, playing, a maths question, dying, game over and so on. The phase is just a string in game.phase, and every frame, update does whatever that phase needs:

    • phaseTime resets to 0 on every change, so "show the stage intro for 2.2 seconds" is one comparison.
    • Only the "playing" phase runs the real game. Everything else is a screen that waits.
    • During "question", nothing moves at all, not even the stars or the scrolling ground. The game is frozen behind the question.
    • While power-up cards are showing, pace is 0.35: the whole fight runs in slow motion so the player has time to choose.

    The overlay screens are drawn from the phase too, so adding a phase means a new string, a line in update, and a line in the HUD's list of screens.

    A clock that never resets

    Every 30 seconds of flying, a maths question pops up. Answer it right and the dragon gets a shield, 10 points and a full belly of fire. The obvious way to time that would be the stage clock, round.time. But round.time goes back to 0 every time the dragon dies, and a struggling player would then never see a question. So the game keeps a separate clock just for maths:

    game.mathTime is set to 0 here, when a new game starts, and nowhere else. It lives on game, not on the round, so throwing away a round on death leaves it alone. It only grows in updatePlaying:

    Because it only ticks while playing, it pauses during intros, the "OUCH!" screen and the question itself. Seconds count only when the player is actually flying. Die at 25 seconds and the question still comes after 5 more seconds of play.

    Asking the question

    1. Freeze. The phase becomes "question", so update stops moving anything. updatePlaying calls runQuestion() without await: the loop keeps running (and drawing the frozen scene) while the question waits.
    2. Let go of the keys. keys.clear() forgets whatever was held when the question popped up. When play resumes, the dragon only moves once the player presses a key again, instead of shooting off in whatever direction it was flying before the question.
    3. Wait for a right answer. As in tic-tac-toe, questions.ask only resolves on a correct answer. inputDelay: 300 ignores typing for 0.3 seconds, so a player mashing space doesn't type into the answer box.
    4. Reward and move the target. nextQuestion += 30 sets the next question 30 seconds later, then play resumes with a 2.5-second shield.

    The HUD shows the countdown in the top-right corner, worked out fresh every frame from the same two numbers:

    free comes from edition.js. On your public free arcade the build script sets it, the question code is swapped for one that answers itself at once, and the same timer gives a "BOOST" instead of a maths question.

    Buying a continue

    After the third life, the game-over screen offers a continue: answer continueQuestions (2) questions in a row with questions.askEach, and the dragon gets three new lives on the same stage, keeping its level and power-ups. The score goes back to 0, so the leaderboard always measures one set of three lives.

    QUIZ

    The dragon dies with mathTime at 25 and nextQuestion at 30. When is the next question?

    • 30 seconds into the new life.
    • After 5 more seconds of play.
    • Straight away, as a penalty.

    mathTime lives on game and isn't reset by a new round. It only stops while the dragon isn't playing.

    Does game.mathTime grow while the "OUCH!" screen is showing?

    • Yes, it's added to in update every frame.
    • No. Only updatePlaying adds to it, and that only runs in the "playing" phase.
    • Only on the last life.

    The maths clock counts flying time, not screen time.

    Why does runQuestion call keys.clear()?

    • To stop the player cheating.
    • Because the question needs the keys.
    • So keys held when the question appeared don't keep steering the dragon when play resumes.

    The player's hands have been busy answering. Starting again with nothing held means the dragon waits for a fresh key press.

    Course 3 · Lesson 9

    Monsters as State Machines

    Six monsters, six ways of fighting. The floating eye hovers and fires a beam. The skeleton blinks in, aims and vanishes. The gargoyle sits as stone, then dive-bombs you. Each one is written the same way, as a state machine: the monster is always in one named state, each state does one simple thing, and a timer or an event moves it on to the next. It's the same idea as the game's phases, one level down.

    One object, any kind

    A monster's kind is a number, and that number is also its tile in the monster picture (goblin first, griffin last). It's used as an index everywhere: toughness[kind], points[kind], behaviours[kind]. Every behaviour is an object with two functions: init sets the monster up (where it enters, which state it starts in) and update runs it every frame.

    Small helpers

    approach moves in a straight line towards a point. dx / dist and dy / dist make a direction of length 1 (a "unit vector"), so the monster moves step pixels whichever way it's heading, diagonals included. If the point is closer than one step, it snaps there and reports that it has arrived, so it never overshoots and jitters back and forth.

    The floating eye

    Follow it state by state:

    1. enter: starts above the screen (y = -30) and floats down to its hover height. On arrival, drift.
    2. drift: slides sideways towards the dragon at a lazy 34 pixels a second, bobbing on a sine wave, while its timer counts down. At zero it fires a beam and switches to charge.
    3. charge: holds still for 1.6 seconds while the beam warns and fires. Then it goes back to drift, or after three beams, to leave.
    4. leave: rises off the top. Once it's above y = -40, update returns false and the filter removes it.

    Each if handles one state, and because they run in order, a monster can change state and start the next one in the same frame. m.pace stretches the waiting times, so later stages (pace 0.85) attack sooner.

    Flags for the artist

    The very first line, m.charging = m.state === "charge", doesn't affect the fight at all. It's there for render-foes.js, which draws a red glow round a charging eye. In the same way the orc sets m.windup (it shakes before it throws), the gargoyle sets m.stone and m.awake, and the skeleton sets m.hidden. These little flags are the monster telling the drawing code "warn the player". Every attack in Draconis has a warning like this, so dodging is about reading the signs, not luck.

    Some flags change the rules too. A hidden skeleton can't be hit, and a stone gargoyle bounces fireballs off:

    A defeated monster isn't removed straight away. alive becomes false, and for the next second updateMonster only grows its fade, while the drawing code greys it out, spins it and shrinks it. Then it's filtered away.

    QUIZ

    Why does approach divide dx and dy by dist?

    • To make the monster slow down as it gets close.
    • To get a direction of length 1, so the monster moves exactly step pixels whichever way it goes.
    • To avoid dividing by zero.

    Without it, a monster far away would move much faster than one nearby.

    An eye has just fired its third beam and its charge timer runs out. What happens next?

    • It fires a fourth beam.
    • cycles reaches 3, so it switches to "leave" and floats away.
    • It dives at the dragon.

    m.cycles >= 3 ? "leave" : "drift".

    What is m.charging for?

    • It decides when the beam fires.
    • It makes the eye take double damage.
    • It tells the drawing code to show a warning glow.

    The state machine runs the fight. Flags like this let render-foes.js show what's about to happen.

    Course 3 · Lesson 10

    Monster Shots

    Every monster has its own projectile: lobbed axes, fluttering feathers, beams, bursting boulders, arrow volleys and homing wisps. They all live in one list, round.shots, and they're all plain objects with a type.

    Aiming

    Math.atan2(dy, dx) answers "which way is it?" as an angle in radians (a full turn is 2π, about 6.28). Math.cos and Math.sin turn an angle back into an x and y part. Multiply by the speed and you have a velocity: how many pixels per second to move along each axis. The optional turn twists the aim a little, which is how spreads are made:

    For 5 feathers, i - (count - 1) / 2 runs -2, -1, 0, 1, 2, so the middle feather flies straight at the dragon and the others fan out evenly on both sides. ...aimAt(...) spreads the returned vx and vy straight into the new object. The dragon's spread fire uses the same centring formula.

    One update, many movements

    Every shot moves the same basic way: position plus velocity times dt. Then movers, an object of functions looked up by type, adds anything special. movers[shot.type]?.(...) calls the function only if there is one: an ember or an arrow has no mover and just flies straight. A lookup table like this replaces a long chain of ifs, and a new shot type is one new entry.

    • Axe: gravity adds to vy every frame, so it curves in an arc like a thrown ball.
    • Boulder: once it falls past burstY it marks itself dead and spawns 7 shards in a ring. They go through spawnShots, so they join the list safely after this update.
    • Beam: doesn't move at all. It's a warning line for warnSecs, then a beam for fireSecs, then gone. If the eye is killed during the warning, the beam is cancelled: fair reward for a quick shot.

    An axe that lands where you were

    This is school physics working for a game. Sideways, the axe moves at a steady speed, so it needs distance / time. Downwards, gravity will add ½ × g × t² on its own over the flight, so the throw subtracts that first. The result: the axe is thrown slightly upwards and arcs down onto where the dragon was 1.5 seconds earlier. Keep moving and it misses.

    QUIZ

    With count = 3, what turns does (i - (count - 1) / 2) * 0.22 give?

    • 0, 0.22, 0.44
    • -0.22, 0, 0.22
    • -0.44, 0, 0.44

    (count - 1) / 2 is 1, so i - 1 runs -1, 0, 1. The fan is centred on the aim.

    What happens in movers[shot.type]?.(shot, dt, world) for an ember, which has no entry in movers?

    • It throws an error.
    • Nothing. ?. skips the call, and the ember just flies straight.
    • It uses the axe's mover.

    movers.ember is undefined, and optional chaining doesn't call undefined.

    Why does the boulder add its shards with world.spawnShots instead of pushing them onto round.shots?

    • It's running inside the filter over round.shots, so new shots wait in incoming until it's finished.
    • So the shards make a sound.
    • round.shots is read-only.

    Changing a list while walking through it causes bugs. incoming joins the list after the update.

    Fireballs, Levels and Power-ups

    A belly of fire

    The dragon can't fire non-stop. It stores 3 fireballs, and they recharge one at a time. Firing spends one:

    refillAmmo is a cooldown timer, and it's a pattern worth remembering. A clock counts up by dt while there's something to refill (and sits at 0 when the belly is full). When the clock reaches the refill time, add one fireball and start the clock again. How long that takes depends on the dragon's level:

    ** means "to the power of". At level 1 it's 2 seconds, at level 2 it's 1.8, at level 3 1.62, each level 10% quicker than the last. Math.max(0.5, ...) puts a floor under it, so even a level-30 dragon can't fire faster than twice a second.

    Levelling up

    Kills give XP equal to their points, and staying alive trickles in 1 XP a second. Level 1 needs 23 XP, level 2 needs 31, and so on. It's a while, not an if, because one big kill (a boss is worth 100 or more) can be enough for several levels at once. Leftover XP carries over into the next level instead of being lost.

    firstChoiceLevel is 5 and choiceEvery is 3, so levels 5, 8, 11 and so on each earn a power-up choice. % (remainder) is the "every 3rd" test: it's 0 at 5, 8 and 11, and not in between.

    Three cards to choose from

    The powers are data again: a name, a colour, a description for the card and a max rank. rollChoices drops any power already at its max, shuffles the rest with the same Fisher-Yates loop as the stages, and keeps the first three. A power's rank is just a count in progress.powers, and every effect reads it. Spread fire, for example:

    Each fireball carries its own copy of the powers that matter to it (damage, pierce, homing, size), so the collision code only has to look at the fireball. vy is negative because the fireballs fly up the screen, towards smaller y.

Bugs like this hide well because nothing crashes. Giving damageMonster a damage parameter and using it would fix it.

    QUIZ

    A level-1 dragon (needing 23 XP) with 0 XP gains 30 XP at once. What does addXp return, and how much XP is left?

    • 1, with 0 XP left.
    • 1, with 7 XP left over towards level 3.
    • 2, because 30 is more than 23.

    30 - 23 = 7. Level 2 needs 31, so the loop stops after one level and the 7 carries over.

    The belly is full (3 of 3). What does refillAmmo do to ammoClock?

    • Keeps counting, so the next refill is instant.
    • Holds it at 0, so the cooldown starts fresh after the next shot.
    • Adds a fourth fireball.

    Why is addXp a while loop?

    • To make levelling slower.
    • One big reward can be worth several levels in a row.
    • Because XP can be negative.

    The Wyrm Boss

    After 60 seconds, a rival dragon arrives: the stage's wyrm. It's built exactly like a monster (an object, a state, a timer) with one difference: its list of attacks comes from the stage data.

    The boss has the same fields that damageMonster, canBeHit and the collision code look for (hp, alive, hidden, flash), so all of that code works on it unchanged. It also carries its own radius, r: 38, which hitRadius picks up instead of the monsters' 20. hidden: true makes it untouchable while it makes its entrance.

    Attack, rest, repeat

    • Taking turns again. b.attack counts attacks forever, and list[b.attack % list.length] wraps it round the stage's list. The Crimson Wyrm's list is ["sweep", "dive", "ring", "summon", "dive"], so it dives twice as often as anything else, in a fixed rhythm a player can learn.
    • The state is the attack's name. In any state other than enter and idle, attacks[b.state] looks up the function with that name and runs it. Each attack function returns true once it's finished, and the boss rests in idle before the next one.
    • Enraged. pace(b) is 0.7 once the boss is at half health or below, so its rests get 30% shorter. Some attacks get nastier too.

    Firing on a timetable

    The breath should be one ember every 0.11 seconds. A naive version would fire one ember per frame, which would depend on the screen's frame rate. Instead, due works out how many embers should have been fired by now, and the while loop catches up to that number. On a slow frame it fires two at once; on a fast screen it fires none on some frames. Either way, the stream is the same.

    k goes from 0 to 1 across the stream, and the angle slides from 0.15π to 0.85π (or the other way when flip is true). With y pointing down, those angles aim downwards: the breath sweeps from one side of the dragon's area to the other.

    The ring attack leaves a gap to escape through:

    Sixteen embers evenly round a circle, except where i % 8 is 4 (that's i = 4 and 12). continue skips them, so there are two gaps, opposite each other. The random offset turns the whole ring, so the safe spot moves.

    A checkpoint

    Losing a life against a boss would be miserable if you had to fly the whole minute again. So when the boss appears, game.bossCheckpoint becomes true. On a death, takeHit saves the boss's health in game.bossHp, and newRound (from lesson 4) starts the next life at the boss:

    The timetable is marked as used up, and the stage clock is set one second before the boss is due. spawnFoes then brings the boss in and gives it back the saved health, so the damage you did still counts.

    QUIZ

    The Storm Wyrm's attacks are ["sweep", "ring"]. Which attack is its fifth (b.attack = 4)?

    • sweep
    • ring
    • It has run out of attacks.

    4 % 2 is 0, and list[0] is "sweep". The list repeats forever.

    Why does sweep use due and a while loop instead of firing one ember per frame?

    • To fire as many embers as possible.
    • So the ember stream has the same timing at any frame rate.
    • Because embers are expensive to draw.

    It fires however many embers are due by the clock, which is the same on every screen.

    The dragon dies when the boss has 12 of 50 health left. What happens next life?

    • The stage restarts and the boss has 50 health again.
    • The boss is skipped.
    • The life starts at the boss, and the boss comes back with 12 health.

    Course 3 · Lesson 13

    Scenery, the HUD and the Draw Order

    Painting back to front

    A canvas has no layers or z-index. Whatever is drawn last ends up on top. So draw works like a painter: sky first, then shadows on the ground, then beams (which should sit behind the monsters), the boss, fireballs, monsters, the other shots, explosions, the dragon, the HUD, and finally any full-screen message. This is literally called the painter's algorithm.

    And since the sky is painted first over the entire canvas, it wipes out the last frame. Every frame is a complete, fresh picture.

    Skies and a scrolling ground

    In the low-flight stage, the countryside slides down the screen forever, so the dragon seems to fly forward. scene.scroll grows by 55 pixels a second without end. % tile.height wraps it, so offset always stays between 0 and the tile's height. The tile is drawn twice: once at the offset, and once directly above it. As the first copy slides down off the bottom, the second slides in at the top, and the tile is painted so its top and bottom edges match. No seam, no end.

    That tile, with its river, fields, cottages and trees, is painted once at load time by ground.js, pixel by pixel, into an off-screen canvas. Drawing one finished image per frame is far cheaper than painting 150 trees every frame.

    The trees and fields are placed "at random", but with a seeded generator: seeded(2024) returns a function that gives the same "random" numbers in the same order every time. The countryside looks scattered, yet it's identical on every visit. Math.random() can't be seeded, which is why the game has its own.

    The sky gradients are cached as well: gradient() in scenery.js builds each one the first time and keeps it in a Map, so it isn't rebuilt sixty times a second.

    The heads-up display

    Every bar in the HUD is the same recipe: a dark background box, then a coloured box whose width is the full width times value / max. (width - w) / 2 centres the bar. The bar turns from orange to red when the boss is enraged, so the player can see the danger change.

    The fireball icons draw one per slot, solid for each fireball stored and faded for each one still recharging. The lives along the bottom left work the same way, with 3 - game.deaths little dragons.

    Full-screen messages

    One object maps each phase to its three lines of text, and screens[game.phase] picks the right one. In the "playing" phase there's no entry, so it's undefined, and drawOverlay returns without drawing anything. Lookup tables again: the phase decides, the data describes.

    The whole build, in one sentence: a canvas and its 2D context to paint on, one loop that updates by dt and then redraws everything back to front, plain objects for every thing in the world, held keys read every frame, circles and boxes for collisions, stage data that drives timetables and bosses, small state machines for every monster, and a maths clock that keeps ticking across every life.

    QUIZ

    Why is the dragon drawn after the monsters?

    • It's more important, so the browser draws it faster.
    • Whatever is drawn last ends up on top, so the dragon is never hidden behind a monster.
    • It has to be drawn after the collisions are checked.

    The canvas has no layers. Drawing order is the only thing that decides what's in front.

    The ground tile is 720 pixels tall and scene.scroll is 1500. What is offset?

    • 1500
    • 60
    • 780

    1500 - 720 - 720 = 60. The remainder keeps the offset inside one tile's height.

    Why does the ground painter use seeded(2024) instead of Math.random()?

    • It's more random.
    • A seeded generator gives the same numbers every time, so the countryside looks the same on every visit.
    • Math.random() doesn't work on canvases.

    Same seed, same sequence, same trees in the same places.

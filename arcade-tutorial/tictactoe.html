    Things to notice

    • &lt; ARCADE: a bare < would start a tag, so the "less than" arrow is written as the entity &lt;.
    • The top bar is the same as the picker's, just with fewer buttons. initPage() from ui.js wires up whichever ones are there.
    • The board is empty. Nine squares written by hand would work, but JavaScript creates them, so the HTML and the code can't disagree about how many there are.

    QUIZ

    Why is the back link written &lt; ARCADE?

    • So it shows in the pixel font.
    • A bare < could be read as the start of a tag.
    • Links can't contain symbols.

    &lt; is the HTML entity for "less than". The browser shows < but never mistakes it for markup.

    Why does the HTML leave #board empty?

    • Empty divs load faster.
    • The script creates the nine squares, so the HTML and the code can't disagree about them.
    • Buttons can't be written in HTML.

    The squares also need click handlers that know their own number, which is easiest to set up while creating them.

    What does border: 3px solid currentColor do on .score.cpu?

    • Makes the border black.
    • Makes the border match the page's text colour.
    • Makes the border cyan, the same as that box's own text.

    Course 2 · Lesson 2

    Styling the Board

    Grid lines that aren't lines

    repeat(3, 1fr) makes three equal columns. The nine buttons flow into them, three per row, with no row rule needed. Here's the trick: the board's background is cyan, the squares are dark, and there's an 8px gap between them. The cyan showing through the gaps and padding is the grid. No borders, no lines to draw.

    aspect-ratio: 1 keeps the board square at any width, and width: min(100%, 360px) lets it shrink on small phones.

    The squares

    display: grid; place-items: center is the shortest way to centre one thing (the X or O) both ways inside a box. Buttons come with their own border and font, so both are reset.

    A ghost X on hover

    Read the selector one piece at a time. It matches a .cell that is:

    • :empty: has no text yet (nobody has played there),
    • :enabled: isn't disabled (it's your turn and the game isn't over),
    • :hover: under the mouse,

    and then ::after adds a faint pink "X" inside it. You see where your move will go before you click, and there's no JavaScript involved at all.

    Marks and the winning line

    JavaScript adds x, o and win classes; CSS decides what they look like. The winning squares turn yellow and flash: 4 is the number of times the animation runs, so it flashes for 2 seconds and then stays yellow.

    QUIZ

    Where do the cyan lines between the squares come from?

    • Each .cell has a cyan border.
    • The board's cyan background shows through the 8px gaps.
    • An SVG drawn behind the board.

    The squares are dark and the board is cyan, so the gaps look like lines.

    When does the faint X appear in a square?

    • Whenever the mouse is over any square.
    • When the mouse is over an empty square that isn't disabled.
    • After the CPU has moved.

    All three conditions (:empty, :enabled, :hover) must be true. Taken squares and a finished board never show it.

    How long does the winning line flash for with animation: flash 0.5s steps(1) 4?

    • 0.5 seconds
    • Forever
    • 2 seconds

    Each run is 0.5s and it runs 4 times. Afterwards the normal yellow background stays.

    Every way to win, written down

    There are only eight winning lines: three rows, three columns and two diagonals. Instead of clever code to work them out, they're simply listed. Short, obvious data often beats a clever formula.

    Course 2 · Lesson 4

    Building the Board with JavaScript

    Creating elements

    document.createElement("button") makes a new button that isn't on the page yet. The code sets it up, then boardEl.append(cell) puts it inside the board. Nine times round the loop gives nine squares, and the CSS grid lays them out.

    Why buttons?

    The squares could have been <div>s with click handlers, but buttons come with a lot for free: you can reach them with Tab and press them with Enter or Space, screen readers announce them as buttons, and disabled stops them working with one line. type = "button" is just good habit, so they would never try to submit a form.

    Each square remembers its own number

    () => onCellClick(i) is a small function that runs later, when the square is clicked. By then the loop has long finished. So which i does it use?

    Because the loop uses let, every pass round the loop gets its own i. The function for square 4 "closes over" the i that was 4, and keeps it. A function that remembers variables from where it was made is called a closure.

    The classic bug. With for (var i = 0; ...) there's only one i shared by every pass. By the time anyone clicks, it has reached 9, so every square would call onCellClick(9). let fixes this, which is one reason modern code never uses var.

    QUIZ

    When you click the fifth square, what number does onCellClick receive?

    • 9, because the loop has finished.
    • 4, because that pass of the loop had its own i.
    • 5

    Squares are numbered from 0, so the fifth is 4. let gives each pass its own copy.

    When is a button made by createElement visible on the page?

    • Straight away.
    • Once it's added with something like append.
    • When its className is set.

    A created element lives only in memory until it's attached to the document.

    Which of these do <button>s give you that <div>s don't?

    • A click event.
    • Keyboard focus and Enter/Space presses, plus a working disabled.
    • A grid layout.

    Any element can have a click listener, but only real controls are reachable and usable from the keyboard.

    Course 2 · Lesson 5

    Drawing State to the Screen

    This is the most important idea in the game. The board array is the truth. The buttons on screen are just a picture of it. One function, render(), repaints the whole picture from the state, and it's called after every change.

    Line by line

    • boardEl.children is an HTMLCollection, which looks like an array but has no forEach. [...boardEl.children] spreads it into a real array.
    • mark ?? "": the nullish coalescing operator. If mark is null (or undefined), use "" instead. An empty square shows nothing.
    • cell.className = "cell" wipes any old classes first. Then only the ones that are true now are added. Without the reset, a win class from the last round would stay.
    • mark.toLowerCase() turns "X" into the class x.
    • A square is disabled if it's taken, if the CPU is busy, or if the round is over. Boolean(mark) turns "X" into true and null into false.
    • The aria-label gives screen-reader users the same picture: "Row 2, column 3: O". Rows and columns are counted from 1 here because that's for people.

    The scores

    Object.entries(scoreEls) gives pairs like ["cpu", <strong>]. The arrow function destructures each pair into key and el, then copies score[key] into it. Because the keys of score and scoreEls match, one line handles all three boxes.

    Why redraw everything? It would be a little faster to change only the square that was clicked. But redrawing all nine from the state means the screen can never drift out of step with the game. You never need to ask "did I remember to update that?". With nine squares, the cost is nothing.

    QUIZ

    Why does render write [...boardEl.children] instead of boardEl.children.forEach?

    • The spread is faster.
    • children is an HTMLCollection, which has no forEach.
    • It makes a copy so the buttons can't change.

    Spreading into an array unlocks forEach, map and the rest. (querySelectorAll's NodeList does have forEach, which is why other code can skip it.)

    What is null ?? "empty"?

    • null
    • "empty"
    • false

    ?? uses the right side only when the left is null or undefined.

    What would go wrong if render didn't start with cell.className = "cell"?

    • The squares would lose their grid layout.
    • Nothing.
    • Old classes like win or x would stay on squares in the next round.

    classList.add only adds. Resetting first means the classes always match the current state.

    Finding a Winner

    Which squares are free?

    flatMap is map followed by flattening one level. Returning [] drops an item and [i] keeps its index, so it filters and transforms in one go. For ["X", null, "O", null, null, "X", "O", null, "X"] it gives [1, 3, 4, 7].

    Notice it takes cells as a parameter instead of reading board. That lets the CPU use it on imaginary boards later.

    Has anyone won?

    • lines.find returns the first line that passes the test, or undefined if none does.
    • ([a, b, c]) => destructures each line, so [0, 4, 8] becomes a = 0, b = 4, c = 8.
    • cells[a] && comes first for a reason: three empty squares are also all equal (null === null). Checking that the first one is taken stops an empty row counting as a win.
    • It returns an object with the winning line (for the flashing) and the mark (to know who won), or null.

    Is the round over?

    The order matters. The ninth move can fill the board and complete a line, and that's a win, not a draw. So wins are checked first. recordTicTacToeWin() adds one to the player's leaderboard count (it does nothing for guests).

    QUIZ

    What would go wrong if winnerOf left out cells[a] &&?

    • Diagonals wouldn't be checked.
    • A row of three empty squares would count as a win, so the game would end at once.
    • Nothing. It's just for speed.

    null === null is true, so an empty line would pass. On a new board, the very first line would "win".

    What does emptyCells([null, "X", null]) return?

    • [null, null]
    • [0, 2]
    • 2

    It returns the indices of the empty squares.

    Why does checkEnd look for a win before checking for a full board?

    • The last move can fill the board and complete a line, and that should count as a win.
    • Wins are more common than draws.
    • emptyCells is slow.

    If the draw check came first, a ninth-move win would be scored as a draw.

    Course 2 · Lesson 7

    Taking Turns with async/await

    Waiting without freezing

    A Promise is an object that stands for a result that will arrive later. new Promise((resolve) => ...) hands you a resolve function to call when it's ready. Here, setTimeout calls it after ms milliseconds. So wait(650) is "a promise that comes true in 0.65 seconds".

    Inside an async function, await wait(650) pauses that function for 0.65 seconds. The page doesn't freeze: animations keep running and the browser stays responsive. That's why the game needs a busy flag. Something has to stop the player clicking while the CPU "thinks".

    A click, start to finish

    1. Guard. Ignore the click if a move is already happening, the round is over, or the square is taken. Early returns like this keep the rest of the function simple.
    2. Lock. busy = true, then render(), which disables every square.
    3. Move. Put an X in the state and play a sound.
    4. Check. If that move didn't end the round, let the CPU go, and wait for its whole turn to finish.
    5. Unlock. busy = false and render again. Empty squares come back to life, unless the round is over.

    The CPU's pause is pure theatre: the computer picks its move in a blink. 650 milliseconds of "CPU is thinking..." just makes the game feel like a game.

    Look closely: checkEnd() calls endRound(...) without await. That's deliberate. endRound goes off and runs its own slow story (a pause, then a maths question), while onCellClick finishes straight away. over is already true, so the board stays locked anyway.

    QUIZ

    While await wait(650) is pausing cpuTurn, what happens to the rest of the page?

    • Everything freezes until the wait is over.
    • It keeps running normally. Only that function is paused.
    • The page reloads.

    await pauses the async function and lets the browser get on with everything else.

    What stops the player placing a second X while the CPU is "thinking"?

    • The wait function blocks clicks.
    • busy is true: render() disables every square and onCellClick returns early.
    • Nothing. It's a bug.

    Two layers: disabled buttons don't fire clicks, and the guard catches anything that slips through.

    What does wait(1000) return?

    • undefined, after one second.
    • The number 1000.
    • A Promise that resolves after one second.

    It returns straight away, with a promise. await is what waits for it.

    Course 2 · Lesson 8

    Minimax: a CPU That Looks Ahead

    How does the CPU choose a square? It plays out every possible rest of the game in its head, and picks the move that turns out best assuming you also play your best. Tic-tac-toe is small enough to do that completely. The method is called minimax.

    Recursion

    minimax calls itself. Every recursive function needs base cases, places where it stops and answers directly:

    • Someone has won: return a score.
    • The board is full: it's a draw, return 0.

    Otherwise it tries each empty square in turn: place the mark, ask minimax to score the position after that move (with the other player to go), then undo the move with cells[i] = null. Trying a move and taking it back is called backtracking. It lets one array stand in for thousands of imaginary boards.

    Max and min

    On the CPU's turn it picks the highest score (good for it). On your turn it assumes you'll pick the lowest (good for you). That's the "mini" and "max" in the name. It never hopes you'll make a mistake.

    Why 10 - depth?

    depth counts how many moves into the future we are. A CPU win scores 10 - depth, so winning next move (depth 1, score 9) beats winning in three moves (depth 3, score 7). A loss scores depth - 10, so losing later is "less bad" than losing now. Without this, the CPU might dawdle when it could win at once.

    Picking the move

    • [...cells] makes a copy to experiment on, so the real board is never touched.
    • Each possible CPU move is scored, then all moves that tie for the top score are returned. Choosing randomly between equally good moves stops the CPU playing exactly the same game every time.
    • Math.max(...array): Math.max wants separate numbers, so the array is spread into them.

    QUIZ

    Why does minimax set cells[i] = null after the recursive call?

    • To clear the board for the next round.
    • To undo the imaginary move before trying the next one.
    • Because the move was bad.

    This is backtracking. Without the undo, every imaginary move would pile up on the same array.

    When it's your turn in the search, which score does minimax assume you'll choose?

    • The highest.
    • The lowest, which is the worst for the CPU.
    • A random one.

    It assumes you play perfectly against it, so it plans for your best reply.

    The CPU can win now (depth 1) or in three moves (depth 3). Which scores higher?

    • Winning now: 9 beats 7.
    • Winning later: 7 beats 9.
    • They score the same.

    10 - depth rewards quicker wins.

    Course 2 · Lesson 9

    Making the CPU Beatable

    A perfect tic-tac-toe player can never lose. The best you could ever do against it is a draw, which isn't much fun. So the arcade's CPU makes mistakes on purpose:

    Rolling the dice

    Math.random() gives a number from 0 up to (but not including) 1. With aiMistakeChance at 0.2 in config.js, Math.random() < 0.2 is true about one time in five. Turning the dial is one change in one file: 0 makes a perfect CPU, 1 makes one that always blunders when it can.

    What counts as a mistake

    worse is every empty square that isn't one of the best moves. Sometimes there aren't any (all the free squares are equally good), so worse.length > 0 falls back to the best moves. Without it, options could be an empty array and the CPU would pick undefined.

    Picking at random from a list

    This is the standard recipe. For a list of 3, Math.random() * 3 is somewhere from 0 to just under 3, and Math.floor rounds it down to 0, 1 or 2, each equally likely: exactly the valid indexes.

    QUIZ

    What happens with aiMistakeChance: 0?

    • The CPU always makes mistakes.
    • The CPU always plays a best move, so you can't beat it.
    • The CPU picks squares at random.

    Math.random() < 0 is never true, so blunder is always false.

    What values can Math.floor(Math.random() * 4) produce?

    • 1, 2, 3 or 4
    • 0, 1, 2 or 3
    • Any number from 0 to 4

    Random times 4 is from 0 to just under 4; rounding down gives a whole number from 0 to 3.

    Why check worse.length > 0?

    • To make the CPU blunder more often.
    • Because filter can return null.
    • If every free square is a best move, there's no mistake to make, and picking from an empty list gives undefined.

    Then it just plays one of the best moves.

    Course 2 · Lesson 10

    Ending a Round and the Question Gate

    Ending a round

    • score[result] += 1 uses bracket notation: result is a string like "draw", so this is score.draw += 1. One line serves all three outcomes.
    • The result shows for 1.4 seconds so you can see the winning line flash.
    • await questions.ask(...) opens the maths question. That promise only resolves once a question is answered correctly: askQuestion in questions.js keeps asking new ones in a while (!correct) loop. Tic-tac-toe doesn't need to know any of that. It just waits.
    • Then the Play again button appears, and gets the keyboard focus so Enter starts the next round.

    Where questions comes from

    gameQuestions is shared by every game. It looks up which question bank the teacher has assigned to "tictactoe" and returns an object with loaded (a promise for when the bank is ready) and ask. In your free arcade, the build script swaps the question code for a stub whose ask resolves at once, so the same tictactoe.js runs with no maths at all.

    A new round

    Reset the state, then render. Because render draws everything from the state, there's nothing else to clean up: the old marks and the flashing line vanish by themselves.

    Starting up

    1. initPage() checks the session and wires up the top bar. No session, no game.
    2. Build the nine buttons and hook up Play again.
    3. Wait for the question bank. The game can't let you play a round it has no way to finish, so the first round only starts once questions are ready. Until then, the status still says "Loading...".
    4. If the bank fails to load, the board is drawn locked (over = true) and the status explains the error instead of failing silently.
    The whole build, in one sentence: HTML gives the page its parts, CSS gives the look, the state variables hold the truth, render() paints the truth, click handlers change it, async functions pace it, and shared modules handle sessions, sound and questions so the game file only has to be a game.

    QUIZ

    If result is "cpu", what does score[result] += 1 do?

    • Adds a new key called result to score.
    • Adds one to score.cpu.
    • Throws an error.

    Brackets use the variable's value as the key. score.result would use the literal name "result".

    When does await questions.ask(...) finish?

    • As soon as the question appears.
    • After any answer, right or wrong.
    • Once a question has been answered correctly.

    Wrong answers bring a new question. The promise resolves only on a right one, so Play again stays hidden until then.

    Why does start() wait for questions.loaded before the first round?

    • To make the page look busy.
    • A round ends with a question, so the game shouldn't start one until questions can be asked.
    • buildBoard needs the questions.

    And if loading fails, the error is shown and the board stays locked.
